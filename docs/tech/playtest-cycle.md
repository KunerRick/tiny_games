# 试玩-打磨闭环：台账驱动的维度循环

> 适用：反复「试玩出报告 → 开发修复 → 独立复核」，把一款游戏从「能玩」打磨到「精致」。
> **触发方式**：说 **「试玩循环」**（或「跑一轮试玩」「继续处理试玩报告」），
> 或直接用斜杠命令 `/playtest <游戏> [维度]`（例：`/playtest mithril ui`）。
> 协议正文：本文（版本化、可提交）。
> 五维方法 / 达标清单：[`playtest-dimensions.md`](./playtest-dimensions.md)。
> 当前状态：各游戏台账见 [`../plans/playtest-ledger-index.md`](../plans/playtest-ledger-index.md)
> （每款一份 `playtest-ledger-<game>.md`，全局问题编号也在索引里分配）。
> 本地入口：`.claude/skills/playtest-cycle/SKILL.md`（gitignored，只做指针）；斜杠别名：`.claude/commands/playtest.md`。

## 0. 为什么不该再用两个会话

原来的流程里，人承担的是**传输层**：把报告粘给开发、把结论粘回试玩。这一步不产生任何判断，
却要求人全程在线。Claude Code 已经有够用的原语：

| 原语 | 在闭环里的角色 |
|---|---|
| `Agent`（fresh subagent） | 试玩者 / 系统验证者 / 数值分析师 / 复核者。干净上下文，且可用浏览器 + MCP |
| 主会话 | 调度者 + 开发者（读报告、改代码、跑自检、更新台账） |
| 文件（`docs/plans/*-playtest-*.md`） | 交接协议。报告是证据，台账是状态 |
| `SendMessage` | 需要让同一个子代理继续（保留它的上下文）时用 |

**不需要**：`/loop`（定时心跳，不是状态机）、`fork` 子代理（继承开发者结论，等于没复核）。

## 1. 三种「轮」——先把时间尺度分开

| 单位 | 定义 | 默认预算 | 结束标志 |
|---|---|---|---|
| **拍 (pass)** | 一次试玩 → 修复 → 复核 | 40–90 分钟 | 见 §10.1 |
| **批 (batch)** | 一次调用里连跑几拍，聚焦同一个维度 | 3 拍或 90 分钟 | 维度收敛 / 预算用尽 / 阻塞 |
| **阶段 (phase)** | 可玩 → 稳定 → 精致 → 发布 | 跨维度，15–30 拍 | 见 §10.3 |

「最多 3 轮」指的是**单批预算**，不是项目上限。一个维度没打磨完，用户说「继续」就进入下一批；
不要让模型因为「已经 3 拍了」自行宣布完成，也不要无限自我修复到上下文耗尽。

## 2. 硬约束（违反会白跑一轮）

1. **串行**：预览服务（`http://127.0.0.1:7456/`）与 Cocos MCP 都是单例，同一时刻只能有一个角色
   操作浏览器/编辑器。不要为了「省时间」把试玩和修复并行。
2. **在执行目录里改代码**：Cocos 编辑器只编译它启动时打开的工程目录，worktree 里的 `.ts`
   改动预览看不到。除非明确要求在 worktree 里做，否则一律在当前工作目录改。
3. **复核者必须是 fresh 上下文**：用 `Agent` 新建（`subagent_type: "claude"` 或 `"general-purpose"`），
   **不要用 `subagent_type: "fork"`**。试玩者 / 系统验证者 / 数值分析师同理。
4. **试玩者不改任何 `.ts` / 场景 / 预制体**，只产报告。修复是主会话的职责。
5. **子代理的简报必须自包含**：它看不到本会话历史。游戏名、场景名、台账路径、上一轮报告、
   本轮焦点维度、验收标准、双轨规则都要写全。
6. **收尾关浏览器**：子代理结束时必须 `browser_close`。后台跑完不关的 headless Chrome +
   软件渲染 Cocos 会烧到 600% CPU（已知事故）。
7. **拍前快照存档**：开始前导出 `localStorage` 存档快照（`addInitScript` 方式恢复），
   并区分「干净档」与「进度档」两个 profile。清档、注入、debug 收尾都要在报告里声明。
8. **改过 `.ts` 先 `project_refresh_assets` 再整页 reload**，否则预览跑旧代码。

## 3. 角色

| 角色 | 谁扮演 | 关注 | 交付物 |
|---|---|---|---|
| 玩家 / QA | fresh 子代理 | UI、交互手感、首次体验、bug | 轮次报告（含界面巡检表、覆盖声明） |
| 系统验证者 | fresh 子代理 | 玩法：每个系统是否可达、可感知、有取舍、闭环、边界 | 系统盘点表 + 规格偏差 |
| 数值分析师 | fresh 子代理 | 数值：脚本输出 + 三进度点实测 vs 设计预算 | 测量表 + 偏差分类（within / watch / defect） |
| 复核者 | fresh 子代理 | 台账 `open` 项逐条 + 回归冒烟 + 建议状态变更 | 报告「复核」章节或 `-reverify.md` |
| 开发者 | 主会话 | 修复、跑自检、更新台账 | 代码 + 自测证据 + 台账变更 |

**级别变更权**：开发者不得单方面把 P1 降成 P2 来通过闸门。级别变更必须由复核者确认；
开发者不同意时保留原级别，在台账写「异议 + 理由」。

## 4. 两根轴：级别与打磨分

| 轴 | 取值 | 回答的问题 | 用途 |
|---|---|---|---|
| 级别 | P0–P3 | 能不能玩 / 会不会误导 | **发布闸门**与修复优先级 |
| 打磨分 | 0–3 | 离精致还有多远 | **收敛判据**与冻结决策 |

级别定义（沿用仓库口径）：

- **P0** 玩家会直接放弃（卡死、无法继续、白屏、必崩）
- **P1** 严重误导 / 主流程受阻（提示与判定矛盾、关键按钮无响应）
- **P2** 明显打磨问题（文案错、状态不同步、面板不刷新）
- **P3** 细节瑕疵 / 建议

打磨分定义与每维达标线见 [`playtest-dimensions.md`](./playtest-dimensions.md) §0.4 / 各维末节。
**不要把两者混用**：一个不阻断主流程但「像半成品」的纯文字屏，是 P2 + 打磨分 1，不是 P1。

## 5. 焦点选择与维度轮转

每拍只选**一个焦点维度**，另带一轮回归冒烟。默认顺序（新游戏相反：先玩法）：

```
UI → 玩法 → 交互 → 数值 → 稳定性/回归 → （回到最低分 / 有覆盖缺口的维度）
```

选择规则（按优先级）：

1. 用户指定了维度 → 用它；
2. 台账有「下一批建议焦点」→ 用它；
3. 否则选**打磨分最低**的维度；同分选**最久没做全量**的；
4. 有「未覆盖」界面 / 系统时，优先补覆盖，再谈提分。

不要把五个维度塞进一拍——那是浅扫，产出的报告会像「我点过这个界面」。

## 6. 台账（可变状态）

路径：`docs/plans/playtest-ledger-<game>.md`；索引与全局编号：`docs/plans/playtest-ledger-index.md`。
**报告是 append-only 的证据，台账是唯一的状态源。** 新游戏复制
[`playtest-ledger-TEMPLATE.md`](../plans/playtest-ledger-TEMPLATE.md)。

台账必须包含：

```markdown

| ID | 级别 | 打磨分 | 维度 | 状态 | 引入轮 | 关闭轮 | 证据 |

## 4. 收敛指标（每拍）
| 拍 | 日期 | 焦点 | 新开 P2+ | 关闭 | 净增 | 回归 | 新增覆盖 | stop_reason |

## 5. 冻结 / 解冻记录

## 6. 环境与存档约定（预览地址、存档键、profile、快照方式、已知工具坑）

## 7. 下一批建议焦点 + 理由
```

状态枚举：`open / fixed-pending-review / verified / deferred / wontfix / regressed / watch`。

- `deferred` / `wontfix` 必须写原因和复查条件；
- `watch` 用于数值观察项（超容差但设计上可接受），不是缺陷；
- 复核者只建议变更，主会话落账；有分歧时保留原状态 + 异议。

**编号分配**：唯一源是 `playtest-ledger-index.md` 的「全局下一编号」。开工前读它，新问题从该编号起，
本轮结束时把下一编号写回索引。**不要**在协议或 SKILL 里硬编码「现在到 N 几」。

## 7. 报告（append-only 证据）

路径：`docs/plans/YYYY-MM-DD-playtest-round<N>-<dim>-<scope>.md`，`<dim>` 取 `ui / gameplay / interaction / balance / stability / regression`，
`<scope>` 用游戏 id 或更细的入口。**问题编号跨轮连续**，从台账索引起算。

报告必须包含：

### 7.1 问题清单（机读区）

```markdown
| ID | 级别 | 打磨分 | 维度 | 游戏 | 场景/入口 | 现象 | 复现步骤 | 期望 | 证据 |
|----|------|--------|------|------|-----------|------|----------|------|------|
| N91 | P2 | 1 | ui | mithril | 营地 → 铁匠铺 | 页签无图标 | 地图点营地 → 切五页 | 页签带图标 + 下划线 | r25-02 / 探针 `_tabLabels` |
```

### 7.2 界面巡检表（UI 轮必填，普通轮也建议）

逐屏一行，不能写「都看过没问题」。字段与判定规则见
[`playtest-dimensions.md`](./playtest-dimensions.md) §1.2–§1.3。

### 7.3 覆盖声明（必填）

```markdown
## 覆盖声明
- 本轮到达：营地五页 / 装备 / 饰品 / 天赋 / 技能 / 战斗 HUD / 死亡结算
- 未到达：胜利结算（两次远征均阵亡）
- 不可达：区域 BOSS（推荐装等 12，本轮最高 Lv4）
- 使用的声明式捷径：无 / 注入存档 {level:12, ilvl:12} 进入 BOSS（目的：验阶段转换；不影响纯净路径结论）
```

### 7.4 方法与数据说明

视口、坐标换算（每轮现场标定）、是否清档 / 注入 / debug、探针字段、控制台错误数、截图编号对照。
未复现的疑点单列一节，不要混进问题表。

> 本版之前的旧报告不需要重写：它们保持 append-only 证据身份，状态由台账承接。
> 新报告从本版起使用 `<dim>` 文件名与「打磨分 / 维度」两列。

### 7.5 截图与产物（本地证据，不入库）

- 截图统一放 `docs/assets/<YYYY-MM-DD>-<game>-round<N>/`；该目录由 `.gitignore` 的
  `docs/assets/*-round*/` 规则排除，**不进版本库**（一轮 20+ 张、几 MB，且对读代码的人无用）。
- 报告里照常写相对链接（`../assets/…png`），它只是**本机查阅指针**：远端仓库 / PR 里点不开是预期的，
  不要把「链接失效」当成缺证据。需要给别人看图时单独贴，不要为了链接把图提交进去。
- 提交范围：报告 `.md` + 台账 + 代码 / 配置。截图、录屏、`.playwright-mcp/` 产物一律不提交。
- 拍前拍后都检查 `git status`：确认没有把 `docs/assets/*-round*/` 加进暂存区（`git add -A` 最容易带进去）。

### 8.2 系统验证者（玩法）

> 你是**系统验证者**，不是开发者，也不看本轮 diff。你的输入是设计规格、台账的系统盘点表、当前工程。
> 逐个系统回答五个问题：① 正常进度内可达吗？② 使用后有可感知结果吗？③ 存在有意义的取舍吗？
> ④ 结果与面板文案一致吗？⑤ 空态 / 满态 / 资源不足 / 重复操作成立吗？
> 规则同 §8.1（串行、真实输入、声明式捷径、browser_close）。
> 产出：系统盘点表（`已覆盖 / 部分覆盖 / 未覆盖 / 不可达`）+ 规格偏差清单，按 §7 登记问题。

### 8.3 数值分析师（数值）

> 你是**数值分析师**。不看本轮 diff，只信脚本输出与实测读数。禁止用「感觉难 / 感觉慢」下结论。
> 步骤：
> 1. 跑 [`playtest-dimensions.md`](./playtest-dimensions.md) §4.2 列出的脚本，记录输出与计数；
> 2. 在三个进度点（新档 Lv1 / 首个区域 BOSS / 第二区域入口）各实测 10–15 分钟，
>    用声明式捷径构造接近真实的存档并写明注入内容；
> 3. 填 §4.4 测量表，与设计预算对照，偏差分 `within / watch / defect`；
> 4. 核对结算面板每一行收益之和与实际存档增量（逐字段）。
> 产出：测量表 + 偏差清单 + 建议区间。结束时 `browser_close`。

### 8.4 复核者

> 你是**独立复核者**。你只拿到：台账、本轮报告、开发者的 `git diff`、当前工程。
> 不要相信报告或 diff 里的自述，逐条用浏览器 / MCP / 脚本读回验证。
> 重点回答：① 台账里所有 `fixed-pending-review` 与上一轮 `open` 项是否真的修好（给证据）；
> ② 修复有没有引入新问题（回归冒烟 10 项，见 §5.2）；③ 声明式捷径是否最小、是否掩盖了真实缺陷；
> ④ 报告里有没有「说法对但玩家实际遇到的是另一回事」的错位；⑤ 维度打磨分是否该调整。
> 产出：报告「复核」章节或 `-reverify.md`，并给出建议的台账状态变更（不直接改台账）。
> 结束时 `browser_close`。

## 9. 主会话的调度流程

```
0. 读台账 → 确定焦点维度（用户指定 > 台账建议 > 最低分 / 最久未全量）
1. 确认前置：预览在跑（lsof）、MCP 在线（server_get_server_status）、存档快照已导
2. 按焦点选角色 → Agent(简报) → 等报告落盘 → 读机读表 + 覆盖声明
3. 按 P0 → P1 → P2 → P3 处理，同级按打磨分从低到高；**单拍修复上限 5 条 / 90 分钟**
   - 改完立刻跑 `npx tsc --noEmit`（或编辑器自带 tsc，见 AGENTS.md）
   - 有对应纯逻辑自检的跑 `node tools/verify-<game>-core.js`；数值相关跑 §4.2 脚本
   - 场景/预制体改动走 MCP，改完 `validate_scene`
   - 未修完的写 `deferred + 原因`，不要硬修到失控
4. Agent(复核者简报) → 读复核结论 → 建议台账状态变更
5. 主会话落账（状态、覆盖、打磨分、收敛指标、下一批焦点）
6. 判断停止（§10）：继续下一拍 / 换维度 / 结束本批 / 交给用户
7. 收尾：`git diff --stat` 检查范围、按仓库规范提交、更新全局编号索引
```

**试玩进行时主会话可以做什么**（串行不等于空等）：读设计规格与历史报告、跑纯逻辑脚本
（只写 `temp/`，不动 `assets/`）、整理台账、写修复方案。**不要** `project_refresh_assets`、
不要保存场景、不要改 `.ts`（编辑器会热重载，污染正在进行的试玩）。

## 10. 结束条件

### 10.1 单拍

| 条件 | 类型 | 动作 |
|---|---|---|
| 出现 P0 / 复核发现回归 P1 | **硬停** | 不得进入下一拍，先修 |
| 预览 / MCP 不可用 | 硬停 | 报告阻塞，不自行拉起编辑器 |
| 焦点维度清单全过 + 新开 P0/P1 = 0 + 新开 P2 全部处理或显式 deferred + 复核无回归 | **正常收敛** | `stop_reason=converged` |
| 修复量达 5 条 / 90 分钟 | 软停 | 剩余项 `deferred`，`stop_reason=budget` |
| 报告与探针矛盾且无法调和 | 软停 | 回到诊断，`stop_reason=blocked` |

**单个未关闭的 P2 不阻塞一拍结束**——它进台账排队，否则一拍会膨胀成大杂烩、复核质量下降。

### 10.2 一个维度何时算「打磨完」

五个信号同时满足，状态置 `frozen`：

1. **覆盖完备**：台账中该维度的所有界面 / 系统不是「未覆盖」；
2. **新问题枯竭**：连续 2 拍该维度新开 P2+ ≤ 1，且无 P1；
3. **回归为零**：连续 2 拍复核无回归；
4. **规格对齐**：设计规格中该维度条目全部有实测证据；
5. **达标线全绿**：该维度 rubric 全部通过（见 `playtest-dimensions.md`）。

冻结后只做冒烟（§5.2），不再深挖；只有回归或设计变更才解冻并记录原因。

### 10.3 全局

| 阶段 | 判据 |
|---|---|
| 可玩 | P0/P1 = 0，主流程跑通 |
| 稳定 | 稳定性维度 = 3，连续 2 拍无回归 |
| 精致 | 五维打磨分全部 ≥ 3 或全部 frozen |
| 发布 | 全维度 frozen + 构建产物冒烟（`check-wechat-build.js` + 实机）通过 |

**边际收益判据**：连续 2 拍新开 P2+ 不降反升 → **停止试玩，回到设计 / 实现诊断**。
继续玩只会扩大面积，不会收敛。

**预算兜底**：单批 3 拍 / 90 分钟；触顶不是失败，写 `stop_reason=budget` + 下一批建议后停，
用户说「继续」再续。所有停止都要写 `stop_reason`（`converged / budget / blocked / blocked-by-user`），
防止「跑累了」被当成「打磨完了」。

## 11. 不该用这个流程的场景

- 只是想快速看一眼某个改动 → 直接改完自己验，不用起试玩者。
- 全站 20+ 款游戏的确定性大扫 → 适合 Workflow（需用户显式说「用 workflow」），但**仍然必须串行**。
- 定时轮询 → 那是 `/loop` 的事，不是状态机。
