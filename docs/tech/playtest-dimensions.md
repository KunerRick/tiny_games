# 试玩打磨：五维方法与达标清单

> 配套协议：[`playtest-cycle.md`](./playtest-cycle.md)。协议管**流程与状态**（拍 / 批 / 阶段、台账、报告格式、停止条件），
> 本文管**每一维怎么测、测到什么算完**。
>
> 维度固定五个：**UI / 玩法 / 交互 / 数值 / 稳定性**。每拍只选一个焦点维度，另带一轮回归冒烟。
> 另有一条**横跨五维的旅程线**（§6 体验分）：它不问「这一屏做得怎么样」，只问「玩这一趟值不值」。
> 维度分够了但旅程线不动，说明东西齐全却没劲——那时该改玩法或数值，不是继续修界面。
> 新游戏入册时按 §7.3 生成自己的系统盘点表。

---

## 0. 通用约定

### 0.1 覆盖优先于深挖

一个永远到不了的界面，比一个没细看的界面危险得多。每拍开始前先看台账的**覆盖矩阵**：
优先补「未覆盖」，再谈「已覆盖项的打磨分」。试玩者必须交出**覆盖声明**（到达 / 未到达 / 不可达及原因），
不能只写「看过没问题」。

### 0.2 双轨：纯净路径 vs 声明式捷径

| 轨道 | 用途 | 规则 |
|---|---|---|
| 纯净路径（默认） | 证明玩家真的能到达、能获得 | 只走游戏自身输入；禁止改金币 / 血量 / 道具 / 存档字段 |
| 声明式捷径 | 补齐正常进度到不了的界面（高等级 BOSS、胜利结算、资源不足分支） | 允许注入存档或调 debug 入口，但**必须在报告里逐项声明**：注入了什么、目的、是否影响判定；且该界面在某一轮的纯净路径中至少到达过一次 |

捷径不是作弊，**未声明的捷径**才是。复核者要检查两点：注入是否最小、有没有掩盖真实缺陷。
禁止的仍然是「用捷径伪造进度后，把结论当成纯净路径的证据」。

### 0.3 证据三级

按可信度从高到低：

1. **脚本输出**（`node tools/verify-*.js` 的 `*_OK` 与计数）——可复现、可回归；
2. **页内探针读回**（`window.cc` 读组件 / 私有字段 / 坐标 / 文本）——证明「引擎里真的是这个值」；
3. **截图**——证明「玩家眼里真的是这样」。

每条问题至少占两级；UI 问题必须有截图 + 一条读回（文本 / 坐标 / 尺寸 / 颜色），不能只有截图。
截图文件名要与断言一致（例：`r24-14-burst-2` 实为 2/96 濒死红闪），错位要在报告里更正。

### 0.4 打磨分 0–3

级别（P0–P3）回答「能不能玩 / 会不会误导」，打磨分回答「离精致还有多远」。两条轴正交，都要记。

| 分 | 含义 | 玩家会怎么说 |
|---|---|---|
| 3 | 精致 | 「这个做得挺用心」 |
| 2 | 可接受（**默认达标线**） | 「能用，没毛病」 |
| 1 | 粗糙 | 「像半成品 / 有点难受」 |
| 0 | 半成品 | 「这也能上？」 |

打磨分是**界面 / 系统级**的，不是单条问题的分数。一条问题可以附带它把哪个界面从几分拉到几分。
修复排序：先 `级别`（P0 → P3），同级按「打磨分低 → 高」。

### 0.5 每维的输出物

| 维度 | 主角色 | 必交产出 |
|---|---|---|
| UI | 玩家 / QA | 逐屏巡检表 + 截图编号 + 每屏打磨分 |
| 玩法 | 系统验证者 | 系统盘点表（可达 / 可感知 / 有意义选择 / 闭环 / 边界）+ 规格偏差 |
| 交互 | 玩家 / QA | 交互清单逐项结果 + 中断 / 恢复 / 拒绝路径证据 |
| 数值 | 数值分析师 | 脚本输出 + 三进度点实测表 + 与预算的偏差 |
| 稳定性 | 玩家 / QA + 脚本 | 回归冒烟 10 项 + 控制台 / 构建 / 存档迁移结果 |
| 旅程（跨维，每拍都记） | 玩家 / QA | 旅程日记 + 四项体验分 + 同一旅程脚本的用时段与卡点数（§6） |

### 0.6 体验分 0–3（旅程级，玩家侧）

打磨分是**界面 / 系统级、开发侧**的（「这一屏做得怎么样」）；体验分是**旅程级、玩家侧**的
（「这一趟玩得值不值」）。两条都要记，因为它们的组合才指明下一步改什么：

| 组合 | 含义 | 下一步 |
|---|---|---|
| 打磨分高 + 体验分低 | 东西齐全但没有玩下去的理由 | 玩法维（缺取舍 / 缺成长）或数值维（曲线平），**不是继续修 UI** |
| 打磨分低 + 体验分高 | 手感对了但糙 | UI / 交互维，性价比最高 |
| 两条都低 | 还没到打磨阶段 | 先回到「能不能玩通」 |
| 两条都高 | 该维度可冻结 | 转下一维 |

四项固定问题与打分口径见 §6.2。体验分不做加权总分——四项分开记，取**中位数**与**最低项**。

## 1. UI / 视觉完善度

### 1.1 要回答的问题

- 这一屏**看起来**完成了吗？哪些元素只有文字、没有图形 / 图标 / 品质色 / 空态？
- 状态看得出来吗（选中 / 禁用 / 已拥有 / 冷却 / 锁定 / 低血）？
- 反馈与事件成比例吗（被打 1 点 vs 被打 30 点）？
- 排版有没有压盖、出界、字号分裂、留白不均？

### 1.2 逐屏巡检表（必填）

不是「我点过这个界面」，而是「这个界面有哪些元素、缺哪些、哪一处不对」：

```markdown
## 界面巡检（逐屏）

| 界面 | 入口 | 已有元素（图标/图形/文字/动效） | 缺失或缺陷 | 级别 | 打磨分 | 截图 |
|------|------|--------------------------------|------------|------|--------|------|
| 营地 → 铁匠铺 | 地图 → 营地 | 标题 + 5 个文字页签 + 列表 | 页签无图标；设施头部无图形 | P2 | 1 | r24-02 |
```

**本轮范围内每个能到达的界面都要有一行和至少一张截图**；不能合并成「营地五页都看了」。

### 1.3 判定规则

按 [`design/2026-11-10-ui-art-style-guide.md`](../design/2026-11-10-ui-art-style-guide.md)：

| 现象 | 级别 | 打磨分 | 说明 |
|---|---|---|---|
| 纯文字屏：整屏只有 `Label` 与纯色矩形，没有 `Graphics` / 图标 | 至少 P2 | 1 | 「像半成品」；主界面出现直接 P1 |
| 纯文字按钮：页签 / 主操作只有文字，没有图形或第二重选中信号 | P2/P3 | 1–2 | 选中态不能只靠一种信号 |
| 反馈过度：全屏红闪 / 震屏与伤害量无关 | P1/P2 | 1 | 干扰判断 |
| 反馈不足：扣血、拾取、技能就绪、低血没有任何视觉 / 听觉反馈 | P1/P2 | 1 | 关键事件必须可感知 |
| 状态不同步：置灰 / 选中 / 禁用与逻辑不一致，或只靠文字 | P2 | 1–2 | 点击被拒要有反馈 |
| 排版：压盖、出界、同一层级两种字号、留白不均 | P2/P3 | 1–2 | 放大 200% 复核 |
| 对比度：关键图形 / 文字与底色接近，需放大才看清 | P3 | 2 | 选中态换对比墨色是常见修法 |

### 1.4 达标线

- 总体 ≥ 2；
- **主操作路径上的按钮**必须有图形或明确的状态外形（不能是纯文字）；
- **关键事件**（受伤、拾取、升级、技能就绪、低血、胜负）必须有可见反馈，且强度与事件量级相关；
- 不允许存在「纯文字主界面」；
- 本轮新增 / 改动的界面不得引入出界与压盖。

### 1.5 常见误判

- 「玩家说大厅是空的」可能指**游戏内面板**，不是大厅——先逐屏定位，再改。
- 红闪只铺在战场矩形内、HUD 不被染色时，应写「整个战场泛红」，不要写「整个屏幕都红」。
- 选中态底色 = 图标同色时，图形会「整块消失」——这是 N88 的教训，必须用对比墨色。
- 截图编号会因多次 reload 错位：报告里要写「编号 → 实际内容」对照表。

## 2. 玩法 / 系统

### 2.1 要回答的问题

- 设计规格里的每个系统，玩家在正常进度中**真的会遇到并用到**吗？
- 用了之后**有可感知的结果**吗？结果与面板文案一致吗？
- 存在**有意义的取舍**吗，还是某个选项永远最优？
- 系统之间有**组合效果**吗（装备 × 饰品 × 天赋 × 职业）？
- 空态 / 满态 / 资源不足 / 重复操作这些边界成立吗？

### 2.2 系统盘点表（从设计规格生成）

试玩者不读代码，但**要读设计规格**。把规格里的每个系统拆成一行：

```markdown
| 系统 | 规格章节 | 玩家入口 | 自动覆盖 | 上次实测轮 | 状态 |
|------|----------|----------|----------|------------|------|
| 饰品协同 | §7.3（12 条） | 角色 → 饰品 | `verify-mithril-trinkets.js`（692 项） | round16 | 已覆盖 |
| 区域 BOSS | §5.4（3 只） | 地图底部节点 | `verify-mithril-balance.js` | 未实机 | 未覆盖 |
```

**状态**：`已覆盖 / 部分覆盖 / 未覆盖 / 不可达（原因）`。这张表进台账，不只在单轮报告里。

### 2.3 每个系统的五个验证点

1. **可达**：在正常进度内能进入；到不了就标「不可达」并说明需要什么等级 / 资源。
2. **可感知**：使用后玩家能看见 / 听见结果（数值、文案、图形、音效至少两项）。
3. **有意义选择**：至少两个选项在不同场景下互有优劣；如果一个永远最优，记「伪选择」。
4. **闭环**：选择 → 结果 → 下一轮决策；面板写的收益必须等于实际入账（这类「口径不一致」是高频缺陷）。
5. **边界**：空态、满态、资源不足、重复操作、跨系统组合各试一次。

### 2.4 秘银远征的系统盘点（种子）

| 系统 | 验证点 | 已有自动覆盖 | 备注 |
|---|---|---|---|
| 战斗基础（移动 / 普攻 / 4 技能 / 资源 / 受击 / 无敌帧） | 五职业技能差异、资源循环、死亡转换 | `verify-mithril-core` | 手感项放交互维度 |
| 4 职业 × 6 技能 | 技能可感知、资源限制、变体改变行为 | `verify-mithril-core` / `-dungeons` | 变体内容 7/24，属内容缺口 |
| 装备（8 槽 / 品质 / 词条 / 改造 / 重铸 / 分解 / 满包） | 品质色、词条效果可感知、满包折算 | `verify-mithril-core` / `-camp` | 品质色分支在 round24 未实机取证 |
| 饰品（20 件 / 12 协同 / 两槽 / 替换） | 每件效果、协同点亮、替换提示 | `verify-mithril-trinkets`（48 场自动战斗） | round16 实测过部分 |
| 天赋（3 系 × 5 层 × 2 选 1 / 洗点） | 已投 / 可投 / 锁定三态、洗点回流 | `verify-mithril-core` | 面板可读性见 UI 维 |
| 营地（铁匠铺 / 附魔台 / 训练场 / 厨房 / 军需官） | 每设施首个可用等级、材料收支、场次加成 | `verify-mithril-camp` | 经济不变量在脚本里 |
| 悬赏（24 条 / 4 类 / 刷新） | 指标可达成、领取扣减、跨日刷新 | `verify-mithril-bounty` | |
| 野外（12 节点 / 补给 / 事件 / 宝箱 / 篝火 / 区域门槛） | 走法、补给耗尽、节点类型收益 | `verify-mithril-wild`（2828 项） | |
| 副本（6 个 × 3 遭遇 + BOSS / 首通） | 阶段推进、首通奖励、重复通关 | `verify-mithril-dungeons`（4×6 自动通关） | |
| 区域 BOSS（3 只 / 阶段） | 推荐装等、阶段转换、结算提示 | `verify-mithril-balance` | 低装等 TTK 是观察项 |
| 存档迁移（v1→v2 / 坏档 / uid 冲突） | 各版本档可进、字段不丢 | `verify-mithril-balance` | |
| 音效 / 震动 | 11 类发声、10 类静默、开关即时 | `verify-mithril-audio` | |

### 2.5 好问题与坏问题

| 坏（不可执行） | 好（可验证） |
|---|---|
| 「饰品系统不够有意思」 | 「装两件不同 tag 但没有对应协同时，协同栏写『两件同 tag』，与两格 tag 矛盾（N54）」 |
| 「装备感觉没用」 | 「同部位从 8 装等换到 12 装等，面板 DPS 不变 / 实战击杀时间不变」 |
| 「BOSS 太难」 | 「装等 7.5 打推荐 12 的 BOSS，TTK 约 140 s；同装等打小怪 DPS 25」 |
| 「新手引导不好」 | 「首战不操作 30 s 内阵亡两次，提示只说『按住普攻』，没有说『边走边打』」 |

### 2.6 达标线

- 规格内每个系统状态不是「未覆盖」；
- 没有「伪选择」（某选项在全部场景占优且无代价）；
- 面板收益与实际入账一致（逐字段核对，不是抽样）；
- 空态 / 满态 / 不足态都有明确文案，不静默。

## 3. 交互 / 手感

### 3.1 要回答的问题

- 输入有没有被吃掉、点偏、延迟？
- 中断（暂停 / 返回 / 切后台 / 刷新 / 断线）之后，状态与文案是否一致？
- 被拒绝的操作有没有反馈？
- 反馈强度与事件量级成比例吗？

### 3.2 交互清单

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 点击命中：按钮实际可点区域 ≥ 视觉区域，缩放后仍可点 | 点边缘 / 角落 |
| 2 | 按下态：按下有视觉变化（缩放 / 变色） | 截图对比 |
| 3 | 连点 / 快速切换：不重复结算、不叠加动画、不卡死 | 10 连点 + 快速切页签 |
| 4 | 拖拽：起点 / 终点 / 阈值 / 取消 | 桌面结束事件是 `TOUCH_CANCEL`；抬起仍在起点内是 `TOUCH_END`；监听挂共同父级 |
| 5 | 「拖了个空」：横移超过阈值但没拖到东西 | 必须退回点击回调，不能静默吃掉 |
| 6 | 模态遮挡：遮罩不吞掉返回 / 关闭；返回键层级在遮罩之上 | 点遮罩外、点返回 |
| 7 | 暂停 / 继续：时间、敌人、冷却全部静止并恢复 | 探针前后对比 |
| 8 | 返回路线图 / 返回大厅 / 切后台 / 刷新：生命、补给、进度、奖励口径一致 | 每个出口各跑一次 |
| 9 | 禁用态：置灰 + 点击有提示，不能无反应 | 资源不足 / 等级不够 |
| 10 | 拒绝路径：条件不满足有 toast / hint，文案说清缺什么 | 逐条触发 |
| 11 | 输入等价：键盘 / 鼠标 / 触摸都能完成主流程 | 至少两种输入 |
| 12 | 反馈比例：伤害 / 事件量级 → 红闪 / 震屏 / 音效分级 | 小伤害 vs 重击 |
| 13 | 关键反馈：低血、技能就绪、拾取、升级、胜负可感知 | 余光可见 / 可听 |
| 14 | 首帧与加载：黑屏 / 白屏 / 半初始化按钮不可点 | 冷启动 |
| 15 | 性能：Graphics 重绘、粒子、长列表滚动不掉帧 | FPS 覆盖层 |

### 3.3 方法

- **探针**：读 `_paused`、`phase`、`playerHp`、`supply`、`retreat`、按钮 `active` / 颜色，证明状态机一致。
- **事件包装**：包 `rend.onEvents` 记录 `damage` / `heal` / `pickup`，核对视觉反馈与实际事件。
- **帧采样**：对 `_hurtFlash` / `_shake` 做 rAF 采样，证明「强度与伤害相关」而不是只看代码。
- **真实输入**：能用 `page.mouse` / `page.keyboard` 就不用内部方法；必须用内部方法时在报告里声明。

### 3.4 达标线

- 清单 1–15 项全部有结果（通过 / 缺陷 / 不适用 + 原因）；
- 每个「中断 / 退出」出口的存档字段与提示文案一致；
- 不存在「无反馈的拒绝」与「与量级无关的强反馈」。

## 4. 数值 / 平衡

### 4.1 原则：不靠感觉，靠曲线和预算

「玩了十分钟觉得有点难」不是数值结论。数值维度的产出必须是**可复现的测量值 + 对照预算的偏差**。
仓库已经把纯逻辑层做成确定性可模拟（`*Core.ts` 禁 `Math.random` / `Date.now`），
先用脚本跑，再进游戏抽点。

### 4.2 先跑脚本

| 脚本 | 回答什么问题 | 何时跑 |
|---|---|---|
| `node tools/verify-mithril-balance.js` | 长跑稳定、六副本计时、3 区域全清、一周目 6 小时预算、经济不变量、存档迁移 | **每拍开始前** |
| `node tools/verify-mithril-dungeons.js` | 4 职业 × 6 副本自动通关矩阵 | 改战斗 / 敌人数值后 |
| `node tools/verify-mithril-trinkets.js` | 4 职业 × 6 副本 × {不戴, 戴} 48 场自动战斗 | 改饰品效果后（3–5 分钟） |
| `node tools/verify-mithril-camp.js` | 设施材料收支、经济不变量 | 改营地成本后 |
| `node tools/verify-mithril-core.js` | 数值曲线、副属性预算、天赋规则 | 改任何核心数值后 |

脚本通过只证明「不崩、不越界、在配置区间内」，**不证明「好玩 / 合理」**。后者靠下面两步。

### 4.3 三个进度点抽点

固定选三个有代表性的进度点，每点实测 10–15 分钟：

1. **新档 Lv1**：首战、初始经济、第一件装备；
2. **首个区域 BOSS**（推荐装等附近）：门槛是否可跨、TTK、死亡次数；
3. **第二区域入口**：等级门槛、装备更新速度、材料缺口。

抽点必须用**声明式捷径**构造接近真实的存档（例如把等级 / 装等调到门槛附近），
禁止直接改「战斗结果」类字段。构造方式写进报告。

### 4.4 测量表

| 字段 | 说明 |
|---|---|
| 战斗时长 / TTK | 从进战到胜负的秒数；BOSS 分阶段记录 |
| 玩家 DPS / 承伤 | 探针累计伤害 / 时间 |
| 通关用时 | 与脚本的 `maxSeconds` 对照 |
| 金币 / 经验 / 材料速率 | 每小时或每场 |
| 升级用时 | 从 LvN 到 LvN+1 的场次 / 分钟 |
| 死亡次数与原因 | 站桩 / 越级 / 机制 |
| 补给经济 | 每节点消耗、篝火恢复、耗尽惩罚 |
| 面板 vs 实际 | 结算面板每一行收益之和与实际存档增量逐字段核对 |

### 4.5 与预算对照

- 设计规格 / 验收记录里已有的预算（副本 30 s ≤ t ≤ `maxSeconds`、一周目约 6 小时、设施材料 70/120/60）
  直接引用；
- 没有预算的项，**先提出建议区间并记进台账**，再判定。默认容差 ±20%，规格另有规定从其规定。
- 偏差分三类：`within`（容差内）/ `watch`（超容差但设计上可接受，例如用推荐装等标签缓解）/ `defect`（明确不合理）。

### 4.6 常见数值缺陷

- **越级墙**：推荐装等标签写了，但实际 TTK 远超可接受区间，玩家只能刷。
- **站桩惩罚**：新手按提示操作仍被秒杀；或完全不操作反而没有惩罚。
- **伪成长**：升级 / 换装后面板数值变了，实战击杀时间不变。
- **口径不一致**：结算面板收益之和 ≠ 实际入账（首通、满包折算、材料溢出是高发区）。
- **经济断裂**：某一材料只进不出，或某个设施永远升不起。
- **支配策略**：某职业 / 饰品 / 天赋在所有副本都最优。

### 4.7 迭代与复核

改常数 → 跑 §4.2 脚本 → 在 §4.3 的三个点重新抽点 → 复核者独立复跑脚本并抽 1 点。
判定从「感觉」变成「数值回归」：同一存档、同一 bot、同一时长，前后读数可对比。

### 4.8 达标线

- §4.2 脚本全绿；
- 三个进度点均有测量表，且没有未解释的 `defect`；
- 面板与实际入账逐字段一致；
- 不存在支配策略（或已作为设计选择记录在案）。

## 6. 体验 / 吸引力（旅程级，跨维）

### 6.1 为什么单列

「这游戏没劲」不属于任何单一维度：UI 巡检全绿、系统盘点全绿、没有 bug，玩家依然可能第二局都不想开。
把它塞进玩法维会被写成「系统完备性检查」，塞进数值维会变成「曲线偏差」，两种都测不到动机。
所以每拍都要跑**同一条旅程**并给四个分——它不替代焦点维度，而是给焦点维度的结论加一个「值不值」的坐标。

### 6.2 四项固定问题（每拍由试玩者答，0–3）

| # | 问题 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|
| E1 | **再开一局的欲望**：现在还想不想再来一趟？ | 马上想再来，已经在想下一局怎么打 | 可以再玩，但不主动 | 能玩，但没有再来的理由 | 只想退出去 |
| E2 | **方向感**：下一步该做什么清楚吗？ | 清楚，且知道为什么 | 清楚该点哪，但不懂意义 | 得试 / 猜 | 完全不知道该干嘛 |
| E3 | **成长可见**：这一趟比上一趟多了什么？ | 数值 + 手感都能感到变化 | 数值变了但没有感觉 | 只有数字在涨 | 没变化 |
| E4 | **张力节奏**：挫败与回报的起伏舒服吗？ | 有惊无险、赢下来有成就感 | 平，但不难受 | 要么无聊要么憋屈 | 令人烦躁 |

**打分纪律**：
- 「还行吧」= 2，不要凭心情给 3；3 的门槛是「我会主动再做一次」。
- 允许某一项为 1（那是要修的信号），但要写清具体是什么让人难受，别写「整体一般」。
- 四项里 E1 与 E3 是**动机项**，权重最高；E1 掉到 1 时，本拍就该开玩法 / 数值问题，而不是收 UI 的尾。

### 6.3 旅程脚本（必填，跨拍不变）

没有固定脚本，跨拍的「新问题数」与 E1–E4 都不可比。每款游戏在首次建账时定一条 **15–20 分钟主线**，
之后每拍**都跑同一条**（换维度不换线）：

```markdown
## 旅程脚本 · <game> v1（2026-XX-XX 定稿，改动需在台账记录原因）
1. 清档 → 新档进入（0–3 分钟：看是否知道该干什么）
2. 完成第一场胜利（首次正反馈何时到来）
3. 第一次强化 / 装备（第一次「变强」可感知吗）
4. 连续 3 次失败或推进到第一个门槛（挫败曲线）
5. 回到大厅 / 退出（收尾是否干净）
```

每拍的报告里记一张表：

```markdown
| 段 | 计划时长 | 实际用时 | 死亡 / 卡点数 | 新发现 | E 分（本段感受） |
|---|---|---|---|---|---|
| 1 新档 | 3 min | 4 min | 卡 1 次（不知点哪） | 2 | E2=1 |
```

**同一脚本连续 3 拍内不得改**；确实要改（加了新系统 / 新手引导重做）就在台账写「脚本 v2 + 改动原因」，
并把前后两拍的产率分开记，不要混成一条趋势线。

### 6.4 常见误判

- **把「我玩得很熟」当成「新人也能玩」**：试玩者是 fresh 上下文，但他一旦学会操作就回不去了。
  第 1 段的分数要在**第一次接触**时打，不要等熟手了再补。
- **把「内容不够」当缺陷**：变体只做了 7/24 是内容缺口（台账记 `deferred`），不是本拍的 P2，
  除非它让主线变得重复（那时写「第 2 小时体验同质化」并归 E3）。
- **只记坏不记好**：四项分数都要有依据句子，好的段落也要写（「第 3 段变强可感知，因为面板数字 + 打击手感都变了」），
  否则下一拍不知道哪些不能动。

### 6.5 达标线

- 四项中位数 ≥ 2，且**没有任何一项为 0**；
- 连续 2 拍四项均不下降，且 E1 不低于上一拍；
- 旅程脚本每一段都能走完（没有「卡住被迫退出」）；
- 达标只说明「可以冻结该维度的体验侧」，不代表可以停——平台期判据见协议 §10.3。
