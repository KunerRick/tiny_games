## 1. 品类与核心循环

**gate runner / count runner（数值门跑酷）**，代表作《Count Masters》《Number Gates》。
用户原始描述：「往前走，发射子弹，左右两边都有选择，是 ×2 或者 ÷2 或者 +20」。

```
自动前进 → 左右两扇数值门（可能带附加效果）→ 横移选一边 → 数值变化 / 挂上 buff
        → 遇到挡路敌人（步兵 / 盾兵 / 刺客 / 再生）→ 停下对拼
          （我方 dps 扣敌人血，对准金色弱点可放大输出 / 敌人持续消耗我方人数）
        → 第 3、6 对门之后弹三选一升级卡（世界冻结）→ 继续前进
        → …… → 终点 Boss（三阶段）→ 结算（通关 / 全军覆没）
```

乐趣不在操作精度，而在**数值滚雪球的决策**：每次二选一都在「现在更强」和「之后更稳」之间下注。

四条**主动发力点**（2026-11-01 可玩性升级，见 §3.7 / §3.8）：

- **集火**：点一下屏幕 = 短时 dps ×2.2（冷却 4.5 s）。对拼阶段原来纯挂机，现在「打得快 = 掉得少」
- **完美连击**：连续选到更优的那一侧累计连击，每 3 连击额外给一点人数 —— 让「选对」这件事本身有复利
- **弱点瞄准**：对拼时敌人身上有左右摆动的金色弱点，队伍停在它下方 dps ×1.8 —— 复用横移输入，不加新手势
- **三选一升级卡**：第 3、6 对门之后各弹一次，在火力上限 / 集火冷却 / 瞄准 / 护甲 / 连击 / 补给里选一张

**单资源设计**：队伍人数 `count` 同时是**火力**和**血量**。

- 火力：`dps = min(count, fireCap)`，每发子弹 1 点伤害，子弹只是表现；`fireCap` 随距离与升级卡成长
- 血量：对拼期间持续扣 `count`
- `count ≤ 0` → 立即 `game_over`（比"走到终点"更常见的失败方式）

于是 ×门同时让你打得更快、更耐打；÷门双重惩罚，选择有分量。

## 2. 代码结构

严格三层，`Config` / `Core` 不 import `cc`，可被 Node 直接编译回归（与 Tetris / 砖块远征 / 合合大作战一致）：

```
assets/games/game_gate_runner/scripts/
├── GateConfig.ts    // 常量、门模板、敌人/速度曲线、计分、色板
├── GateCore.ts      // 纯逻辑：滚动、门触发、对拼、关卡生成、事件
└── GateGame.ts      // Cocos 组件：Graphics 绘制 + 触摸 + HUD/暂停/结算
tools/verify-gate-core.js
```

`GateCore` 对外接口：

```ts
startRun(seed: number): void
reset(): void
step(dt: number): void
setPlayerX(x: number): void
pulse(): boolean          // 集火；不在对局中 / 冷却中 / 三选一打开时返回 false
choose(index: number): boolean   // 三选一选卡；无待选卡或下标非法返回 false
popEvents(): GateEvent[]
// 只读：state / distance / count / countExact / playerX / gates / enemies / boss / score
//      pulseActive / pulseReady / pulseCooldown / pulseRemaining / streak
//      fireCap / aimMult / aiming / armorReduction / activeMods
//      choiceOpen / choiceOptions / streakMultiplier / pulseCooldownMultiplier
```

**确定性**：`mulberry32(seed)`，同 seed 的门/敌人序列逐位相同（回归 #9）。

## 3. 数值与规则

### 3.1 坐标系与镜头

逻辑坐标原点左上、y **向下**（与其它游戏一致）。玩家固定在屏幕 `PLAYER_Y`，世界按 `distance` 向下滚动：

```
screenY(worldY) = PLAYER_Y - (worldY - distance)
```

| 常量 | 值 | 说明 |
|------|----|------|
| `PLAY_W` / `PLAY_H` | 660 / 860 | 与 PlayArea 节点一致 |
| `PLAYER_Y` | 700 | 队伍中心所在屏幕 y |
| `PLAYER_X_MIN` / `MAX` | 90 / 570 | 横移范围（中心） |
| `PLAYER_R` | 26 | 方阵名义半径（仅表现） |
| `SCROLL_BASE` | 300 px/s | 起始速度（原 420，见 §3.5 节奏校准） |
| `SCROLL_MAX` | 440 px/s | 封顶（原 620） |
| `SCROLL_ACCEL` | 0.05 px/s per px | 速度随距离线性增长 |
| `CONTACT_DIST` | 64 | 与敌人"接触"的世界距离（对方 y − distance ≤ 64 即开打） |

### 3.2 数值

| 常量 | 值 | 说明 |
|------|----|------|
| `START_COUNT` | 20 | 初始人数 |
| `COUNT_MAX` | 99999 | 上限（显示/溢出双保险）。22 段局单局能到几万，9999 会过早封顶 |
| `FIRE_CAP` | 60 | **开局**火力上限，之后由 `fireCapAt()` 成长 |
| `FIRE_CAP_GROWTH_PER_PX` | 1/300 | 每前进 1 px 上限 +1/300（8200 px 全程约 +27） |
| `ENEMY_DRAIN_RATIO` | 0.03 | 敌人每秒额外消耗「当前人数 × 该比例」（旧值 0.08，见下方注） |
| `BOSS_DRAIN_MULT` | 1.5 | Boss 的消耗倍率（比例部分同乘） |
| `BOSS_HP` | 1200 | Boss 固定血量（22 段局终局约 6–8 s；300 只够打 1–2 s） |
| `SUBSTEP_SEC` | 1/120 | 固定子步长，避免大 dt 跳门 |
| `MAX_FRAME_DT` | 0.05 | 单帧 dt 上限（切后台回来不一次算爆） |
| `SQUAD_HIT_EVENT_SEC` | 0.2 | `squad_hit` 飘字的产出间隔 |

```ts
fireCapAt(distance, bonus = 0) = FIRE_CAP + floor(distance × 1/300) + bonus
```

> **比例消耗从 0.08 降到 0.03**：0.08 时每场对拼固定掉约 34% 人数，无论人数是 50 还是 500 都一样 ——
> 「攒大数字」在攒起来的那一刻就失效了。降到 0.03 后「固定伤害 + 少量比例」成为主体，
> 人多真的更耐打；同时火力上限随距离/升级成长，大数字重新变成可用资源。
> 拖时间仍然有代价（再生兵会回血，`1/0.03 ≈ 33 s` 是纯比例的天然上限）。

### 3.3 数值门

- 成对出现：左门 `x ∈ [40, 320]`，右门 `x ∈ [340, 620]`，`GATE_W = 280`、`GATE_H = 90`
- 玩家中心 `x < GATE_SPLIT_X(330)` 判为走左门，否则走右门
- 一对门只有**一侧**生效；另一侧同时作废（`used` 双侧置 true），保证「同一对门只触发一次」
- 门板在 `distance ≥ gate.y` 的那一子步触发

门模板池（`GATE_TEMPLATES`，每对随机抽一个模板、左右随机交换）：

| 模板（a / b） | 出现距离 `from` | 设计意图 |
|------|------|------|
| `×2` / `+30` | 0 | 教学：乘法 vs 加法 |
| `×2` / `÷2` | 0 | 经典高风险 |
| `+20` / `+50` | 0 | 纯加法保底 |
| `×2` / `+60`（−伤35%·2战） | 1300 | 少拿一点，换两场减伤 |
| `×2` / `−10`（火力+35%·2战） | 1300 | 挨一刀，换两场爆发 |
| `×3` / `÷2`（火力+50%·2战） | 2600 | 激进：拿一半人换爆发 |
| `+100` / `÷2`（集火−3s） | 2600 | 大数 vs 立刻可用的主动技能 |
| `×3` / `÷3` | 3900 | 高风险：一边暴增一边暴跌，选错要肉疼 |
| `+150` / `−100`（−伤50%·3战） | 3900 | 读秒题：扛过下一个刺客就赚 |
| `×2` / `÷3` | 6500 | 终局前的最后一道坎 |

> `from` 是**世界距离**，段落数从 12 改到 22（§3.5）后整体后移，保证同样的「难度台阶」落在同样的进度百分比上：
> 附加效果侧仍在 ~16% 处首次出现，÷3 与读秒题在 ~48%，最后的 `×2 / ÷3` 在 ~79%。

**附加效果（`GateMod`）一律挂在「立即数字更吃亏」的那一侧**，这是让二选一不再是假选择的关键：

| 类别 | 效果 | 标签 |
|------|------|------|
| `armor` | 每场对拼受伤减免 `value` | `−伤35%·2战` |
| `power` | 对拼 dps ×`(1 + value)` | `火力+40%·2战` |
| `cooldown` | 立即减少集火冷却 `value` 秒 | `集火−3s` |

- `armor` / `power` 只在下一次 `_beginFight` 结算一次，并把该效果 `fightsLeft` 减 1
- 同类效果不叠加数值（取最大值），但场次累加，上限 4 场
- `cooldown` 立即生效，不进驻留列表

> 只有「人数」一个维度时，总有一侧数字更大，玩家永远选它 —— 二选一等于没得选。
> 把另一侧改成「现在少一点、下一战更稳」，选择才真正变成下注。

`applyGateOp(count, op)`：

| 操作 | 规则 |
|------|------|
| `mul` | `count × v` |
| `div` | `max(1, floor(count / v))` —— **除不出 0**，否则一次倒霉的 ÷2 等于直接判负，而玩家那一刻没做错任何事 |
| `add` | `count + v` |
| `sub` | `count − v`，可以打到 0 |

结果统一过 `clampCount()`：NaN / 负数 → 0，超上限 → `COUNT_MAX`，向下取整。
**能把人数打到 0 的只有 `−N` 门和敌人**，这条是回归 #2 的判据。

### 3.4 敌人

敌人分五种类型，除数值差异外各有一个明确的「问题」，玩家在门前就能看到类型标签：

| 类型 | `hpMult` | `atkMult` | `widthMult` | `drainMult` | `regenRatio` | 考题 | 颜色 |
|------|----------|-----------|-------------|-------------|--------------|------|------|
| 步兵 `grunt` | 1 | 1 | 1 | 1 | 0 | 基础 | `#FF6B6B` |
| 盾兵 `shield` | 1.9 | 0.65 | 1.15 | 1 | 0 | dps 上限 | `#FF9A5C` |
| 刺客 `assassin` | 0.55 | 1.9 | 0.9 | 1.2 | 0 | 爆发/减伤 | `#FF4D9E` |
| 再生 `regen` | 1.15 | 0.8 | 1 | 1 | 0.06 | 惩罚拖延 | `#5EE0D0` |
| BOSS `boss` | — | — | — | 1.5 | 0 | 三阶段终局 | `#FF4D6D` |

| 属性 | 公式 |
|------|------|
| `hp` | `round((24 + 0.12 × distance) × hpMult)` |
| `atk`（每秒基础伤害） | `(2 + distance / 800) × atkMult` |
| `width`（只用于绘制，v1 不允许绕行） | `min(420, (260 + distance / 20) × widthMult)` |
| 每秒回血 | `maxHp × regenRatio`（再生兵 6%，其余 0） |
| Boss `hp` | 固定 1200 |
| Boss `atk` | `enemyAtkAt(distance) × 1.5 × BOSS_PHASE_ATK_MULT[phase-1]` |

11 个普通敌人的类型排期（`ENEMY_KIND_POOLS`）：`[步兵]` → `[步兵,盾兵]` → `[盾兵,刺客]`
→ `[刺客,再生]` → `[盾兵,再生]` → `[盾兵,刺客,再生]` → `[盾兵,刺客,再生]` → `[刺客,再生]`
→ `[盾兵,刺客,再生]` → `[盾兵,再生]` → `[盾兵,刺客,再生]`。前期只出步兵，中后期才出现刺客/再生；
最后四场全部是组合池，保证终局前每一战至少要同时应对两种机制。

对拼（`_fight`，每子步）：

```
dps   = min(count, fireCap) × 火力buff × 集火 × 瞄准 × Boss阶段dps
hp   -= dps × dt
hp    = min(maxHp, hp + maxHp × regenRatio × dt)      // 再生兵
drain = (atk + count × 0.03 × drainMult) × (1 − armorReduction)
count -= drain × dt
```

- 敌人 `hp ≤ 0` → 敌人消失、继续前进（Boss 死亡即 `victory`）
- 我方 `count ≤ 0` → `game_over`
- 对拼期间 `distance` 不增长（玩家被"挡住"）
- Boss 血量跨过 66% / 33% 时切换阶段，每阶段只切一次，发 `boss_phase` 事件

### 3.5 关卡生成

`SEGMENT_LEN = 360`、`SEGMENT_COUNT = 22`：

- 偶数段（0/2/…/20）在 `i × 360 + 260` 放一对门
- 奇数段（1/3/…/21）在 `i × 360 + 300` 放一个敌人
- 最后在 `BOSS_DISTANCE = 8200` 放 Boss

即 **11 对门 + 11 个敌人 + 1 个 Boss**，落点互不重叠（回归 #10 校验最小间距 ≥ `GATE_H`）。

**节奏校准（2026-11-07）**：原 12 段在 autopilot 下 17 s 就通关，远低于本章「1–3 分钟」的目标，
「12 段约 40 s」也只是按 620 px/s 的期望值估出来的，实测根本跑不到。改成 22 段并把速度降到 300/440 px/s 后：

| 指标 | 旧（12 段 / 420–620 px/s） | 新（22 段 / 300–440 px/s） |
|------|------|------|
| autopilot（一路优门，不瞄准不集火） | 17 s 通关 | 29 s 阵亡（难度来自玩法深度，不是缺陷） |
| 会瞄准 + 集火的玩家（8 seeds） | — | 61–73 s 通关，人数 6.8k–29k |
| 一路劣门 | 约 20 s 阵亡 | 13–36 s 阵亡 |

> 与设计文档的差异：段数、速度、敌人血量斜率、`BOSS_HP`、`COUNT_MAX`、门模板 `from`、三选一时机全部变了，
> 但**规则结构一个没改** —— 门模板池、附加效果规则、结算公式、三阶段阈值都是原样。
> 校准数据见 §11.3。

**首门教学**（回归 #20）：第一对门固定用「两侧都是加法」的模板，然后**把更差的一侧换到出生点方向**。
旧版初始 `x = 330` 恰好等于 `GATE_SPLIT_X`，站着不动永远走右门，运气好就能不操作通关 ——
现在第一对门必须横移才能拿到更好的一边，第一次教学就建立「我得选」。

### 3.6 计分

```
score = distance × 0.1 + count × 10 + (victory ? 1000 : 0)
```

HUD 距离显示为「米」，即 `floor(distance / 10)`；速度显示为 `round(scrollSpeed / 10) km/h`。

### 3.7 可玩性升级：集火与完美连击

用户反馈「目前只是能玩，可玩性不太高」。原版的问题很具体：**对拼阶段玩家无事可做**（只能看数字掉），
而选门只有"选对/选错"两态、没有连续奖励。两条改动正好补上这两块。

**集火（主动技能）**

| 常量 | 值 | 说明 |
|------|----|------|
| `PULSE_DURATION_SEC` | 1.6 | 生效时长 |
| `PULSE_COOLDOWN_SEC` | 4.5 | 冷却（≈ 2.8 倍时长，必须挑时机） |
| `PULSE_DPS_MULT` | 2.2 | 期间 `dps = min(count, fireCap) × 2.2`，**仍以当前火力上限为基准** |

- 只放大 dps，不改变敌人对我的伤害公式：「打得快 = 掉得少」是唯一收益来源
- 冷却中再点直接返回 `false`，**不重置冷却**（回归 #13 断言 `4.35 → 4.03` 递减）
- 未使用集火时 dps 公式与旧版逐位相同（回归 #5 的 `expectDps = min(count, fireCap)` 不受影响）

**完美选门连击**

| 常量 | 值 | 说明 |
|------|----|------|
| `STREAK_BONUS_STEP` | 3 | 每 3 连击给一次奖励 |
| `STREAK_BONUS_RATIO` | 0.15 | 奖励 = 当前人数的 15% |
| `STREAK_BONUS_MIN` | 5 | 人数少时的保底，避免奖励看不见 |

- 触发门时同时算出**左右两侧**的结果，选中侧严格优于另一侧 → `perfect = true`、`streak++`；否则 `streak = 0`
- 两侧结果相同**不算**完美（避免白送连击）
- 门把队伍打到 0 时不给奖励（否则 `−N` 门会被连击奖励救回来，惩罚失效）
- `gate_hit.after` 是**含连击奖励后**的人数，`bonus` 单独给出奖励那部分，HUD 与实际人数不会对不上
- 选带附加效果的门（§3.3）通常拿不到「严格更优」，**会清零连击** —— 连击从免费糖果变成要付代价的东西

### 3.8 可玩性二次升级：弱点瞄准、敌人类型、三选一、Boss 三阶段

第二轮反馈更具体，定位到两个结构性缺陷：

1. **9 个门模板里有 8 个存在严格优势侧**，二选一是假选择 —— 玩家只需要比大小
2. **人数一旦超过 `fireCap` 就只涨不涨输出，而比例消耗让人觉得人多也没用** —— 攒数字失去回报

对应五条改动（外加两处小修），全部落在核心逻辑与代码绘制里，**不动场景**：

**弱点瞄准**（复用横移输入，不新增手势）

| 常量 | 值 |
|------|----|
| `AIM_DPS_MULT` | 1.8 |
| `AIM_TOLERANCE` | 34（逻辑 px） |
| `WEAK_AMP_MAX` / `WEAK_SPEED` | 96 / 1.5 |
| `BOSS_WEAK_AMP` / `BOSS_WEAK_SPEED` | 120 / 1.1 |

弱点 x 按 `PLAY_W/2 + sin(_time × speed + id × 1.7) × amp` 摆动，钳进 `[PLAYER_X_MIN, PLAYER_X_MAX]`。
「提前就位选门」与「打满输出」因此形成取舍；Boss 的弱点更宽更慢，避免终局变成纯手速。

**敌人类型**：见 §3.4。类型在门前就有标签，玩家可以据此选门（例如「下一个是再生兵，别拿 `÷2` 拖延」）。

**三选一升级卡**

| 卡 | 效果 |
|----|------|
| 火力扩容 | 火力上限 +12 |
| 急速冷却 | 集火冷却 ×0.8（叠乘下限 0.45） |
| 弱点专精 | 弱点倍率 +0.3 |
| 全军护甲 | 每场受伤减免 +15%（上限 45%） |
| 连击狂热 | 连击奖励 ×2（上限 ×4） |
| 紧急补给 | 立即恢复 25% 人数（最少 15） |

- 触发点 `CHOICE_AFTER_GATE_INDEX = [2, 5, 8]`，即第 3、6、9 对门之后各一次（22 段局共 11 对门，
  分别落在中前段 / 中段 / Boss 前）；
  过了 `gate.y + CHOICE_TRIGGER_OFFSET(100)` 才弹，避免和门的反馈叠在同一帧
- 弹出时 `_choiceOpen = true`，`step()` 直接返回 —— **世界冻结**，集火/暂停/移动全部不接受输入
- 选项由确定性 RNG 抽 3 张不重复；`choose(index)` 立即生效并关闭
- **未选卡不能继续**，这是刻意的：强制玩家在「现在需要什么」上做判断
- **为什么不加 3 s 自动选**：一局 3 次 < 4 次（plans 里 G2 的触发条件），停顿成本可以接受，
  强制决策的收益更大。若后续再加长局（≥ 4 次），再启用倒计时。

**Boss 三阶段**

| 常量 | 值 |
|------|----|
| `BOSS_PHASE_2_RATIO` / `BOSS_PHASE_3_RATIO` | 0.66 / 0.33 |
| `BOSS_PHASE_DPS_MULT` | `[1, 0.78, 0.62]` |
| `BOSS_PHASE_ATK_MULT` | `[1, 1.15, 1.45]` |

血量越低，我的输出越低、Boss 伤害越高 —— 终局有明确的「越打越难」的曲线，而不是一条血条磨到底。

**大数字重新有意义**：`ENEMY_DRAIN_RATIO` 0.08 → 0.03、`fireCap` 随距离与升级卡成长（§3.2）。
同时 5 张升级卡里有 4 张直接或间接提升输出/续航，让「攒起来的人数」有地方花。

## 4. 状态机与事件

```
ready → running → (game_over | victory) → 结算面板 → 重来一局 / 返回大厅
```

`GateCore` 产出的事件（`popEvents()` 一次取空）：

```ts
type GateEvent =
  | { type: 'gate_hit';        side: 'left'|'right'; kind: 'mul'|'div'|'add'|'sub';
      value: number; before: number; after: number; y: number;
      perfect: boolean; streak: number; bonus: number;
      mod: GateMod | null }
  | { type: 'pulse' }
  | { type: 'enemy_engaged';   id: number; hp: number; boss: boolean; kind: EnemyKind }
  | { type: 'enemy_destroyed'; id: number; y: number; boss: boolean }
  | { type: 'boss_phase';      phase: 2 | 3 }
  | { type: 'upgrade_chosen';  id: UpgradeId; name: string }
  | { type: 'squad_hit';       amount: number; count: number }
  | { type: 'victory';         score: number; count: number; distance: number }
  | { type: 'game_over';       count: number; distance: number };
```

表现层消费：`gate_hit` → 飘字（`完美 ×N` / `连击奖励 +N` 另起金色一行；带 `mod` 时额外飘一行效果名）；
`pulse` → `集火!` 金色飘字；`boss_phase` → `Boss 强化` / `Boss 狂暴`；
`upgrade_chosen` → 升级卡名字；`squad_hit` → 红字 −N + 队伍抖动；`enemy_destroyed` → 碎屑。

## 5. 输入

| 手势 | 行为 |
|------|------|
| 按住拖动（`TOUCH_START` / `TOUCH_MOVE`） | 队伍中心 x 跟随手指，钳制 `[90, 570]` |
| 轻点（起点到抬起的逻辑位移 ≤ `TAP_SLOP = 12`） | **集火**（dps ×2.2）；点哪里都会先把队伍移过去 |
| 拖动结束 | 只对齐位置，不触发集火 |
| 三选一打开时点卡片 | `_pickCardAt()` 命中三张卡片的矩形 → `core.choose(i)`；手势到此为止（不移动、不集火） |
| 起点落在暂停按钮上 | 整个手势不参与玩法输入（不移动、不集火），交给按钮自己处理 |
| 暂停 / 结算面板打开 / 三选一打开 | `_acceptsPlayInput()` 返回 false，输入穿透被挡住 |

**轻触与拖拽靠位移区分**：桌面拖拽结束派发的是 `TOUCH_CANCEL` 而不是 `TOUCH_END`（踩坑手册 §11），
所以 `END` 和 `CANCEL` 都走同一个 `_finishGesture()`，桌面上"点一下集火"才不会失灵。
`TAP_SLOP` 取 12 逻辑像素：手册 §11.6 实测 8 设计像素的阈值会把"横移 5 CSS 像素"的手势静默吃成拖拽。

触摸节点是 `PlayArea/InputArea`（660×860），面板是它的兄弟节点，打开时不会误触。
`_toLogic()` 用 `convertToNodeSpaceAR` 换算后再加回 `PLAY_W/2`、`PLAY_H/2`。

## 9. 与草案（`plans/2026-10-31-gate-runner-design-draft.md`）的差异

草案是"开工前的一页纸"，实现时按手感与回归数据做了以下调整，**以本文为准**：

| 项 | 草案 | 实现 | 原因 |
|----|------|------|------|
| `FIRE_CAP` | 30 | **60** | 30 时强力 build 也要打 3–4 s 才能清掉一个敌人，节奏拖沓；60 让中后期对拼控制在 1–2 s |
| `SEGMENT_LEN` | 420 | **360** | 8 段 × 420 = 3360 略长；360 让一局约 45–60 s |
| `BOSS_DISTANCE` | 2400 | **3200** | 与段长联动，保证 4 对门 + 4 敌人排满后 Boss 在最后 |
| 敌人 HP 曲线 | `30 + 0.08d` | **`24 + 0.05d`** | 配合 FIRE_CAP 60，让"优门路线"刚好吃得下 |
| 敌人扣血 | 仅 `atk` | **`atk + count × 0.03`** | 纯固定 atk 时人数滚起来对拼无风险；比例给"人多也怕拖"的底，见 §3.2 注 |
| `÷` 保底 | "至少扣 1" | **结果最低 1** | 两种说法都成立，实现按"结果 ≥ 1" |
| 门模板出现距离 | 未定义 | `from` 字段（0 / 720 / 1440 / 2160 / 3600） | 前期只给教学与保底模板 |
| 结算字段 | 草案无 | 分数 / 人数 / 距离 / 最高分 | 与另外三款游戏的结算面板对齐 |
| `SEGMENT_COUNT` | 8 | **12** | 8 段约 20 s 就结束，还没攒起来就通关；12 段约 40 s |
| `BOSS_DISTANCE` | 3200 | **4600** | 与段数联动，Boss 仍排在全部 12 段之后 |
| 主动技能 / 连击 | 无 | **集火 + 完美连击** | 用户反馈"只是能玩，可玩性不高"：对拼阶段无事可做、选门没有连续奖励 |
| 门模板 | 9 个纯数字模板 | **10 个，其中 4 个带附加效果** | 8/9 模板存在严格优势侧，二选一是假选择 |
| 敌人 | 单一类型 | **4 种普通类型 + Boss** | 让"为下一战选门"有依据 |
| Boss | 单血条 | **三阶段（66% / 33%）** | 终局需要"越打越难"的曲线 |
| 人数价值 | `ENEMY_DRAIN_RATIO 0.08`、`FIRE_CAP` 固定 | **0.03 + 随距离/升级成长** | 攒大数字原本没有回报 |

**未做的（v1 非目标）**：点击左右半屏换道、每日挑战固定 seed、音效、排行榜、敌人可绕行。

## 10. 已知平衡观察

- **站着不动能赢**（已修）：初始 `x = PLAY_W/2 = 330`，恰好 `GATE_SPLIT_X = 330`（`<` 判定），
  旧版不动时**总是走右门**，运气好可以不操作通关。现在第一对门固定为「两侧都加法」，
  并把**更差的一侧换到出生点方向**，第一次教学就必须横移（回归 #20）。
  后续门仍是"总有一侧更优"，但第 3、6 对门带附加效果后，最优不等于"数字最大"。
- **弱点与选门的取舍**：对拼时停在弱点下方多 80% 输出，但下一个门很快就到 ——
  经常需要在"再打两秒"和"提前就位"之间取舍。这是刻意保留的张力，不是 bug。
- **横移手感**：手指跟随而非加速度，`PLAYER_X_MIN/MAX` 90/570 留出了 90 px 的边距，
  不会因为贴边而看不清门上的数字。
- **对拼不可躲**：敌人仍占满道路，`_blockingEnemy()` 不判断 x。若横移能躲，
  "人数"就不再是被考核的资源。弱点瞄准放大的是输出而不是闪避，这是刻意区分的。
- **三选一强制停顿**：世界冻结到选完为止，没有"跳过"或超时。一局出现 3 次（第 3/6/9 对门后），
  停顿感换来的是明确的 build 决策；plans 里的 G2（3 s 自动选第一张）触发条件是「≥ 4 次」，
  当前未达到，所以**不启用**——加了反而会把玩家的决策吃掉。若后续再加长局，按该条件重新评估。
- **单局时长**：22 段 / 300–440 px/s 下，会瞄准 + 集火的玩家 60–75 s 通关（模拟 8 seeds），
  远低于旧配置的 17 s。旧配置的问题不是"太快"本身，而是**没时间用上任何 build**：
  第 3 对门才第一次弹卡，而那时已经打完一半。现在 3 次选卡分别落在 ~30% / ~55% / ~75% 的进度处。

**复验中发现并修掉的两个真问题**（都是本轮新加表现层引入的）：

   教训：**SHRINK 标签必须给足高度，且"组件状态对"不等于"像素可见"，验收要看截图。**
