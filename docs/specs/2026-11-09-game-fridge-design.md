# 冰箱底下（Fridge）设计

- 日期：2026-11-09
- 状态：**设计定稿；M1 已实现，门禁 ① 已过、② 已过（2026-11-10 微信模拟器，真机复签留到 M5）、③ 未过（2026-11-10 试玩反馈，待复测）**（M2–M5 未开工）
- 场景：`assets/games/game_fridge/scenes/Fridge.scene`（场景名 `Fridge`）
- 游戏 id：`fridge`；名称：冰箱底下
- 玩法定位：动作 Roguelike · **房间制双摇杆地牢** · 一命通关 + 跨局解锁
- 灵感来源：《以撒的结合》（The Binding of Isaac）的**房间探索 + 道具涌现**；不沿用其题材、名称、美术与数值

> **命名提示**：`fridge` / `Fridge` / 「冰箱底下」均为自造中性标识，不涉及第三方商标。上线前建议做一次商标检索（本项目历史上「雷霆战机」也踩过同名问题）。

## 0. 设计原则（先定不做的事）

| # | 原则 | 含义 |
|---|------|------|
| 1 | **道具靠标签涌现，不靠组合表** | 40 个道具由 14 个标签的交叉规则产生上百种可感知组合；新增道具不改旧代码 |
| 2 | **跨局只解锁内容，不卖数值** | 「冰箱贴」只能解锁角色 / 道具进池 / 挑战模式 / 电梯；**没有永久攻击力加成**，每局起点公平 |
| 3 | **一局一命，死亡即结算** | 只做房间级快照，不做战斗中途的逐实体存档、不做强制复活；紧张感来自「可能全丢」 |
| 4 | **零贴图，纯 Graphics** | 与全部 21 款现有游戏一致；调色板换层，四个世界的观感靠配色与形状实现 |
| 5 | **竖屏单屏一房间** | 720×1280 内一屏一房，不做相机滚动；转场只是 0.15s 推镜 |
| 6 | **先裸手感，后堆内容** | M1 只做一间房；打十分钟不爽就地重做，不允许进入 M2 |
| 7 | **随时可退，回来接着打** | 单局 12–15 分钟，但任意时刻切后台 / 杀进程都不丢进度；存档跨版本兼容，更新后仍可续玩 |

## 1. 一句话玩法

**你是一颗被遗忘的布丁，从冰箱底层一路往下掉**；在失物堆王国的四层地牢里清房间、攒调味料道具、靠标签组合把眼泪变成火球与弹球，一命打死四个 Boss。**随时可以退出，下次回来从最后一间安全房间继续。**

## 2. 差异化定位（为什么不是第三款 Survivor）

| 维度 | 星际弹幕 `shmup` | 雷霆战机 `thunder` | 午夜幸存者 `survivor` | **冰箱底下 `fridge`** |
|------|------------------|---------------------|------------------------|------------------------|
| 空间 | 一屏纵向弹幕 | 一屏纵向弹幕 | 无限大地图 | **房间网格地牢，有回头路与秘密** |
| 时间 | 固定 9 波 | 固定 10 关 | 8 分钟连续计时 | **自主推进，清房才开门** |
| 成长 | 局内捡火力 | 跨局数值升级 | 升级三选一（等级） | **道具永久叠加（无等级）** |
| 操作 | 拖动 | 拖动 + 炸弹 | 单摇杆自动攻击 | **左摇杆移动 + 右半屏拖动瞄准** |
| 死亡 | 结算 | 每关复活一次 | 撑满计时 | **一命，死了全丢** |
| 目标 | 最高分 | 刷星 / 满级 | 活满 8 分钟 | **打穿 4 层 4 Boss** |
| 耐玩来源 | 手感 | 养成 | 构筑 | **探索 + 涌现 + 解锁** |

**与 survivor 的共存逻辑**：一个卖「时间压力」，一个卖「探索赌注」；一个自动攻击，一个手动瞄准。市场里《以撒》与《吸血鬼幸存者》本来就能共存，合集里也一样。

## 3. 世界观与四层结构

> 所有被弄丢的东西，最后都会滚到**冰箱底下**。
>
> 你是其中一颗布丁。往下掉的时候你发现，冰箱底下不是灰尘，是一整个「失物堆」王国——
> 发霉的食物、没人玩的玩具、坏掉的游戏机，都在这里称王。

四层不是并列备选，而是**一局向下推进的四段**：同引擎、换调色板、换敌人表、换该层专属道具池。

| 层 | 名称 | 主题 | 道具语言 | 主色 | 情绪 |
|---|------|------|----------|------|------|
| 1 | **冷藏层 · 发霉食堂** | 腐败食物 | 调味料：辣椒、蜂蜜、跳跳糖、奶酪 | 暗蓝 `#0E1B26` + 暖黄 `#F2C14E` | 可爱、好懂、教学 |
| 2 | **玩具箱 · 发条王国** | 被遗忘的玩具 | 机制件：发条、磁铁、弹簧、电池 | 木褐 `#2A1F17` + 橙 `#E8A33D` | 轻机制、开始有联动 |
| 3 | **游戏机内部 · 坏卡带** | 电子垃圾 | 元游戏：卡带、bug、超频、存档点 | 荧光绿 `#7CFF6B` + 紫 `#C77DFF` | 梗最多、最惊喜 |
| 4 | **压缩机核心 · 冷库深处** | 冰冷机器 | 硬核：霜、铁、压缩、冻结 | 冷灰 `#12141C` + 冰蓝 `#9FE8FF`；唯一的暖红只给 Boss 核心 | 压迫感、以撒式的「越往下越怪」 |

**叙事靠视觉推进**：第 1 层明亮饱和，第 4 层只剩冷蓝与铁灰，没有血、没有宗教符号——既保住「硬核」气质，也不触审核红线。

## 4. 核心循环

```
主界面（继续上局 / 开始 / 角色选择 / 图鉴 / 每日挑战）
   │
   ├─ 有存档 → 「继续上局：第 2 层 · 布丁 · 8 个道具」→ 回到最后一间安全房间
   │
   ├─ 角色选择：血量 / 伤害 / 射速 / 移速 / 主动技能 / 解锁状态
   │
   └─ 开局（种子）
        │
        ├─ 第 1 层：2 选 1 出生道具（从本局可出现的池中）
        │
        ├─ 每层：起点 → 战斗房 ×N → 宝箱房（三选一）→ 商店 / 祭坛 → Boss
        │        └─ 秘密房：在特定墙边放炸弹炸开
        │
        ├─ Boss 击破 → 三选一「核心」（本局永久能力）+ 下一层
        │
        └─ 第 4 层 Boss 击破 → 通关结算
             │
             └─ 死亡 / 通关 → 冰箱贴结算 → 解锁新角色 / 道具 / 模式
```

- 单局 **12–15 分钟**（4 层 × 7 房），单房 **15–25 秒**。
- **任意时刻退出都不丢整局**：见 §13；局内进度存在独立的 `run` 键里，死亡 / 通关才删除。
- 没有层间手动存档：退出即自动落盘，回来从「最后一间安全房间」继续，战斗房内的敌人会重新生成。
- 通关后解锁「电梯」：可从第 2 层开始，代价是少一次宝箱。

## 5. 操作与界面

### 5.1 输入（移动端唯一入口）

| 区域 | 行为 |
|------|------|
| **左半屏按下** | 动态底座摇杆，按下处即圆心；推杆移动，松手归零 |
| **右半屏按下拖动** | 瞄准方向 = 拖动方向；拖动期间手动瞄准并持续开火 |
| **右半屏松手** | 回到**自动瞄准最近敌人**；不拖也能自动打 |
| **右下按钮** | 主动槽：角色技能 / 主动道具共用，**统一充能制**——清 1 房 +1 充能，电池 +2，上限可被道具提高 |
| **右下按钮（炸弹）** | 放炸弹：半径 140 伤害 50、清子弹、炸秘密墙 |
| **右上小地图** | 已探索房间与未探索门；Boss 房标记 |
| **右上暂停** | 暂停 / 音效 / 返回大厅 |

设计要点：

- **自动瞄准是兜底，不是主玩法**：手残玩家单指也能通关第 1 层，但打过第 3 层必须学会拖动微操打背后。
- 双指操作：左摇杆 `_touchId` 与右瞄准 `_aimTouchId` 各自独立，互不抢占（吸取 `SurvivorJoystick` 的单指约定）。
- 按钮层在摇杆层之上，并且按钮的 `TOUCH_END` 不能穿透到瞄准层（用节点层级 + `event.propagationStopped`）。
- 桌面调试：`WASD` 移动、鼠标瞄准 + 左键开火、`Q` 主动、`E` 炸弹（只做调试，不写进玩法）。

### 5.2 界面布局（720×1280）

```
┌─────────────────────────────┐  y=1280
│ ♥♥♥   ●12  ✹2   [小地图]     │  HUD 顶栏 120
├─────────────────────────────┤
│                             │
│        战斗区 9×12           │  504×672
│         （房间）             │  居中
│                             │
├─────────────────────────────┤
│ 道具栏（最近 8 个图标）        │  64
│                    [主动][炸弹]│  右下 160×160
└─────────────────────────────┘  y=0
```

- 道具栏最多显示 8 个图标，超出折叠为「+N」；点击展开列表（含协同提示）。
- 小地图按 **7×7** 网格绘制（与 §6.4 地图生成同坐标系），每格 16px（合计 112px，塞进 120 高的顶栏）；已探索为实心、当前房高亮、Boss 房红色描边、秘密房发现后才画。

### 5.3 界面状态机

`大厅 → 角色选择 → 局内(战斗/拾取/暂停) → 结算 → 大厅`，另有 `图鉴`、`每日挑战`、`解锁树` 三个入口。

## 6. 地牢与房间

### 6.1 房间尺寸

- 逻辑网格 **9 列 × 12 行**，格 56px → 战斗区 504×672。
- 墙厚 24px，门宽 96px，开在四边中点。
- 一屏一房，不滚动；房间转场 0.15s 推镜 + 门锁动画。

### 6.2 每层房间构成

| 层 | 房间数 | 构成 |
|---|--------|------|
| 1 | 7 | 起点 + 4 战斗 + 宝箱 + Boss |
| 2 | 7 | 起点 + 3 战斗 + 宝箱 + **商店** + Boss |
| 3 | 7 | 起点 + 3 战斗 + 宝箱 + **祭坛** + Boss |
| 4 | 7 | 起点 + 3 战斗 + 宝箱 + 祭坛 + Boss |
| 每层 | +1 | **秘密房**（独立于上述计数，需炸墙） |

> 每层统一下调到 **7 房**（原方案 7/8/8/8），一局从 15–20 分钟压到 **12–15 分钟**；第 4 层房间数与前面一致，但敌人血量与密度更高，节奏上「越深越像 Boss 走廊」。特殊房**按层固定**：第 2 层必有商店、第 3/4 层必有祭坛，不做「按种子二选一」，否则小地图与玩家预期不稳定。

### 6.3 房间交互细则（何时触发、何时写档）

| 交互 | 规则 | 写档时机 |
|------|------|----------|
| 进入房间 | 从门跨入 → 0.15s 转场 → 战斗房按波次刷怪并锁门 | 进入瞬间（见 §13.3） |
| 清空战斗房 | 最后一个敌人死亡 → 开门；立刻补 **+1 主动充能** | 清空后 |
| 金币/半心拾取 | 玩家半径 40px 内自动吸附，拾取即结算 | 拾取后 |
| 宝箱三选一 | 走近卡牌 → 点击确认；**选定后另两张消失**，不能反悔 | 选定后 |
| 商店购买 | 点击货位 → 扣币、道具入包；买不起时按钮灰显 | 成交后 |
| 祭坛献祭 | 点击确认 → 扣 1 颗心（2 半心）、给道具；**心不足 2 半心时无法献祭** | 成交后 |
| 秘密房炸墙 | 对秘密房相邻墙放炸弹 → 墙碎、房间揭示并进入小地图 | 炸开瞬间 |
| 层间下行 | 击破 Boss 选完核心 → 楼梯出现 → 踏入后进入下一层起点房 | 进入下一层瞬间 |
| 死亡 / 通关 | 结算屏弹出时删除 `_run` 键（不可续玩） | 结算前 |

### 6.3 房间类型

| 类型 | 规则 |
|------|------|
| 战斗房 | 进门锁门，清空后开门；掉落金币 2–4，30% 掉半心 |
| 宝箱房 | **三选一**道具（比以撒的直接给更友好，也更好做卡牌 UI）；可花 2 金币重掷一次 |
| 商店 | 3 个货位：道具 12–18 币 / 半心 4 币 / 炸弹 3 币；不买可看 |
| 祭坛 | 用 1 颗心换 1 个道具（必定是高价值池）；可拒绝 |
| 秘密房 | 与 ≥2 个房间相邻的空白格；对它的墙放炸弹才开；内含 1 道具 + 3 金币 |
| Boss 房 | 进门锁门；Boss 半血后进入二阶段；击破后三选一「核心」+ 下一层门 |

### 6.4 地图生成（确定性）

1. 在 7×7 网格上，从中心用随机游走生成一棵 **恰好 N 个节点**的树（N = 该层房间数，见 §6.2），保证连通、无环、无重叠；**最多重试 32 次**，超过则丢弃该子种子、用 `mulberry32(seed ^ (floor * 0x9E3779B1))` 派生下一颗继续（保证同一 seed 仍必得同一结果）。
2. BFS 计算每个房间到起点的距离；**Boss = 距离最远的节点**（同距离取索引靠前者）。
3. 特殊房按层固定分配（§6.2），从**叶子节点按离起点从近到远**依次取：先宝箱，再商店（仅第 2 层），再祭坛（第 3/4 层）；若叶子不够，允许从度≥2 的节点里取距离最远的补位。
4. **门由树边推导**：两个相邻房间之间开一扇门（四邻接方向），起点房只在通往邻居的方向有门；不额外造门，小地图直接读同一结构。
5. 秘密房 = 与 ≥2 个房间四邻接的空格；没有合法格时退回「任意只邻接 1 个房间的空格」。**提示规则**：幸运值 ≥ 阈值时，秘密房相邻的墙上出现一道极淡裂纹（`luck` 越高越明显）；炸开后房间进入小地图并写档。
6. 全程 `mulberry32(seed)`；**同一 seed + 同一层号，地图逐字节一致**（可做每日挑战与分享）。
7. 断言（写进自检）：连通、房间数正确、Boss 唯一且最远、每层特殊房类型与 §6.2 一致、秘密房合法、每个非起点房恰有 1–4 个门、门双向对称。

## 7. 战斗规则与数值

### 7.1 玩家基础值

| 项 | 基础值 | 上限 |
|---|---|---|
| 生命 | 3 颗心 = 6 半心 | 12 半心 |
| 伤害 | 3.5 / 发 | 无硬上限，自检要求 ≤ 999 |
| 射速 | 2.5 发/秒（间隔 0.4s） | 6 发/秒（间隔 ≥ 0.08s） |
| 射程 | 340px | — |
| 弹速 | 420px/s | — |
| 散射 | 1 发 | 5 发 |
| 移速 | 215px/s | ×1.6 |
| 受伤无敌 | 0.9s | — |
| 炸弹 | 1 个，上限 9 | — |

**数值公式**（自检直接断言）：

```
dmg      = (BASE_DMG + flatDmg) * dmgMul
rate     = clamp(BASE_RATE * (1 + rateMod), 0.8, 6)
interval = 1 / rate
shots    = clamp(1 + shotsMod, 1, 5)
range    = BASE_RANGE * (1 + rangeMod)
speed    = BASE_SPEED * (1 + speedMod)
```

- 所有修饰器**加法叠加**，`dmgMul` 与 `dmgFlat` 分开累计；任何一项出现 `NaN` / `Infinity` 都视为 bug，自检拦死。
- 幸运 `luck` 只影响：金币掉落概率、宝箱池高价值权重、秘密房提示强度，**不影响伤害**。

### 7.2 命中与碰撞

- 全部圆形碰撞（玩家 r=14、眼泪 r=12、敌人按体型 14–40）。
- 眼泪撞墙消失（带 `bounce` 标签反弹一次，带 `pierce` 穿透敌人）。
- 敌人接触伤害：1 半心 / 次，玩家无敌期内不重复扣。
- 房间边界夹取；玩家不会被弹开穿墙。

### 7.3 死亡

- 生命 ≤ 0 → 0.8s 死亡动画 → 结算（不复活）。
- 结算内容：到达层数、房间数、击杀数、道具列表、冰箱贴收入、图鉴新增。

## 8. 道具系统

### 8.1 数据结构

```ts
export type ItemTag = 'fire' | 'ice' | 'bounce' | 'pierce' | 'explosive'
                    | 'split' | 'homing' | 'chain' | 'poison' | 'shield'
                    | 'speed' | 'luck' | 'heal' | 'shots';

export interface ItemDef {
  id: string;
  name: string;
  floor: 0 | 1 | 2 | 3 | 4;      // 0 = 全局池
  tags: ItemTag[];
  mods?: Partial<Record<'dmgFlat' | 'dmgMul' | 'rate' | 'range' | 'shots'
                       | 'speed' | 'luck' | 'hp', number>>;
  hooks?: Partial<Record<'onFire' | 'onHit' | 'onKill' | 'onRoomClear'
                        | 'onDamage' | 'onEnterRoom', string>>;
  desc: string;                   // 一句话，短到能塞进卡片
}
```

**堆叠规则**：同类修饰器相加；`dmgMul` 相乘但夹到 `[0.25, 3.0]`；同一道具可重复拾取（取最大叠加次数 3）；钩子按拾取顺序触发。

### 8.2 标签协同（写死在规则引擎里，共 14 条）

| 组合 | 效果 | 弹出提示 |
|------|------|----------|
| `fire + explosive` | 火球命中时 60px 爆炸，50% 伤害 | 「焦糖爆裂」 |
| `ice + chain` | 冰弹命中后连锁 2 个目标，各 40% 伤害并减速 | 「霜链」 |
| `bounce + pierce` | 贯穿弹撞墙反弹，可反复命中 | 「弹力针」 |
| `split + homing` | 分裂出的子弹自动追踪 | 「追猎分裂」 |
| `poison + fire` | 中毒目标被点燃时爆燃，范围 80px | 「毒雾爆燃」 |
| `explosive + split` | 爆炸后再分裂 3 个小弹 | 「子母雷」 |
| `shield + heal` | 每房间开始获得 1 点护盾 | 「保鲜罩」 |

### 8.5 数值边界（全部写进自检，违反即失败）

- **生命上下限**：`hp` 恒满足 `1 ≤ hp ≤ maxHp`；提升 `maxHp` 同时等量提升 `hp`；降低 `maxHp` 时若 `hp > maxHp` 则夹到 `maxHp`，且 `maxHp` 最低 2 半心（`corebit` 不会把上限压到 0）。
- **任何自伤都不会致死**：硬糖「咬碎」、祭坛献祭、`overclock` 的进房扣血、热度诅咒等，若当前只有 1 半心则**不扣血也不生效**（相关按钮灰显 / 道具暂不激活）。
- **果冻分裂**：子果冻 HP = 父体当前 HP 的 50%（向上取整），攻击力不变，最多分裂 2 代（防指数爆炸）；子果冻不掉落金币。
- **召唤上限**：单房间同时存活敌人上限 40；召唤类敌人达上限时不再召唤（避免卡顿）。
- **重复道具**：同名道具**最多拾取 3 次**（第 4 次起不再出现在池中），效果按「加法/乘法规则」累计；**上限型修饰器**（散射 5、射速 6/s、移速 ×1.6）一律钳制，自检对 10,000 次随机拾取做不变量断言。

### 10.1 六个角色

| 角色 | 生命 | 伤害 | 射速 | 移速 | 开局道具 | 主动技能（充能制） | 解锁条件 |

| **硬糖** | 3 心 | ×1.35 | ×0.8 | ×0.9 | 锅铲（反弹） | **咬碎**：本房间伤害 +50%，代价掉 1 半心（充能 2，每房最多 1 次） | 首次抵达第 2 层 |

| **冰箱贴**（隐藏） | 1 心 | ×1.2 | ×1.05 | ×1.1 | 磁铁 | **吸星**：把全场敌弹吸成一团金币，最多 20 币（充能 6） | 累计打开 5 个秘密房 |

**特色机制（不是单纯数值差）**：

- **硬糖**：只有 3 心却要贴脸；「咬碎」是高风险爆发，教玩家用血量换输出。
- **冰块**：「融化」——每次受伤移速 −8%，本局累积上限 −40%；受伤越多越难走位，逼玩家学会不挨打。
- **过期酸奶**：**心类回血对它无效**，只能靠**腐坏类道具**回血——判据是道具带 `poison` 标签（当前为 `mold` 发霉面包，每次拾取回 1 半心）。毒对它不造成伤害，改为每层中毒 +5% 伤害（上限 +30%）。
- **冰箱贴**：1 心极限难度，但「吸星」能把弹幕变钱，是贪心流的极致。
- **气泡水**：4 心起步（默认 3 心），比别的角色多一格容错，适合练走位；代价是基础伤害偏低。

### 10.2 角色选择 = 第二层构筑

角色不是「皮肤」，而是**开局就决定了一条构筑倾向**：

| 角色 | 倾向 | 本命标签 |
|------|------|----------|
| 布丁 | 全能 / 位移 | 无（最适合新手） |
| 硬糖 | 高风险高伤害 | fire / explosive |
| 冰块 | 控场 | ice / chain |
| 气泡水 | 弹幕密度 | split / shots |
| 过期酸奶 | 毒 + 腐食回血 | poison |
| 冰箱贴 | 经济 + 幸运 | luck / homing |

| `tiny_games_fridge_run` | 本局快照（§13.2） | 进房、清房、拾取、购买、`onHide` | 死亡 / 通关后**同步删除** |
| `tiny_games_fridge_backup` | 上一次 meta 的备份 | 每次 meta 写入前 | 永久（兜底坏档） |

**键名不带版本号**：`_v1` 一旦写进键名，以后升级就得「读旧键写新键」，最容易丢档。版本号放在**数据内部**的 `schemaVersion` 字段里。

### 13.2 局内快照（RunSave）

只存「运行级状态」，不存敌人 / 子弹 / 特效——当前房间重新生成，代价是敌人满血，但结构极稳。

```ts
export type Dir = 'up' | 'down' | 'left' | 'right';
export type RoomKind = 'start' | 'fight' | 'treasure' | 'shop' | 'altar' | 'boss' | 'secret';

// 与 §14.1 的 FloorMap 同构：省掉 floor（在 RunSave.floor 上）、doors（由 nodes 邻接推导）、depth（BFS 重算）
export interface FloorMapSave {
  w: 7;
  h: 7;
  nodes: { x: number; y: number; kind: RoomKind; cleared: boolean; visited: boolean }[];
  startId: number;
  bossId: number;
  secretId: number | null;
}

export interface RunSave {
  schemaVersion: 2;
  runId: string;              // 随机 uuid，用于幂等与调试
  mode: 'normal' | 'daily' | 'heat';
  seed: number;               // 本局主种子（每日挑战 = 日期种子）
  rngState: number;           // mulberry32 当前状态（uint32）
  charId: string;
  floor: 1 | 2 | 3 | 4;
  startFloor: 1 | 2;          // 「电梯」解锁后可从第 2 层开局
  heatCurses: string[];       // 热度模式三选诅咒；其它模式为空
  map: FloorMapSave;          // 当前层的房间图
  roomId: number;             // 当前所在房间
  enteringFrom: Dir | null;   // 从哪扇门进来（用于恢复站位）
  player: {
    hp: number;               // 半心为单位
    maxHp: number;
    coins: number;
    bombs: number;
    charges: number;          // 主动槽当前充能
    maxCharges: number;       // 由角色 / 道具决定，恢复时用于夹取
    frozenSpeedPenalty: number; // 冰块等角色的累积惩罚
  };
  items: string[];            // 道具 id，按拾取顺序
  activeItem: string | null;  // 主动道具 id（角色技能为 null，用 charId 查表）
  cores: string[];            // Boss 核心
  treasure: { offered: string[]; rerolled: boolean } | null;
  shop: { stock: (string | null)[]; rerolled: boolean } | null;
  savedAt: number;            // Date.now()
  gameVersion: string;        // 写档时的构建版本，仅用于诊断
}
```

**关键点**：

- **必须存 `rngState`**。否则续玩后掉落 / 敌人刷新序列会变，同一局无法复现，也会让「每日挑战」失效。
- 快照体积预估 **< 4 KB**（当前层最多 8 个节点 + 二十来个道具 id），远低于微信 **单 key 1 MB** 与**总量 10 MB** 的限制。
- 反序列化后必须再过一遍 `sanitizeRun()`：房间 id 必须存在于 map、道具 id 必须在表里、HP 夹取、金币非负。

### 13.3 写档时机与防作弊

| 时机 | 写什么 | 目的 |
|---|---|---|
| **进入房间**（门动画结束） | 完整快照（房前状态） | 退出后从这间房开头继续 |
| **清空房间 / 拾取 / 购买 / Boss 后** | 完整快照 | 成果立刻落盘 |
| **`onHide` / 页面隐藏** | 覆盖 `player.hp` 等运行值 + `savedAt` | 切后台被杀进程时保住已受的伤与已有的钱 |
| **死亡 / 通关** | **删除 run 键**（同步） | 一命制；杀进程也不能回滚 |

- **续玩规则**：恢复到最后一次快照的房间，敌人与子弹全部重新生成；**玩家血量保持 `onHide` 时的值**。想靠「快死时杀进程」回血是无效的，因为 `onHide` 已经把你当前的血量写进去了。
- 万一进程被系统直接杀死、`onHide` 没来得及触发（极小概率），最多回到进房时的血量——这是可接受的容错边界，不做逐帧写盘（10 MB 存储也经不起）。
- 写档用**同步** API（微信侧 `setStorageSync`），因为 `onHide` 之后可能没有下一次执行机会。

### 13.4 更新兼容：旧档必须能迁移

```ts
const CURRENT_META_VERSION = 2;
const CURRENT_RUN_VERSION = 2;

export function migrateMeta(raw: unknown): FridgeSave;
export function migrateRun(raw: unknown): RunSave | null;
export function sanitizeMeta(raw: unknown): FridgeSave;
export function sanitizeRun(raw: unknown): RunSave | null;
```

迁移纪律：

1. **只增字段，不改语义**；每加一个字段就在 `migrate*` 里补默认值。
2. 字段改名/换语义时，写显式分支：`if (v === 1) { ... }`，逐级升到当前版本。
3. **遇到未来版本**（用户回退旧包 / 灰度）：不覆盖、不崩溃；把原始 JSON 原样留在备份键里，meta 用默认值起步并提示「存档版本较新，已保留备份」。
4. 读取失败（JSON 坏 / 字段非法）时：**先把原始字符串写进 backup，再回落默认值**，绝不静默丢数据。
5. 每次发布前跑一次「旧档迁移」自检：内置 v1 / v2 样本各一份，断言升到当前版本后字段正确。
6. 小游戏更新本身**不会清空**本地缓存（见 §13.5）；真正会丢的是用户主动删除 / 清缓存，这不是迁移能解决的，只能靠云备份。

### 13.5 微信小游戏的平台机制（2026-11-09 用 curl 核对官方文档）

| 机制 | 官方口径 | 对本作 |
|---|---|---|
| `wx.setStorageSync` / `getStorageSync` | **单个 key 最大 1 MB，所有数据上限 10 MB**；「除非用户主动删除或因存储空间原因被系统清理，否则数据都一直可用」 | **主方案**。Cocos 的 `localStorage` 在微信构建里由适配层转到这里，现有 `StorageManager` 可直接用 |
| 隔离策略 | 「同一个微信用户，同一个小游戏 storage 上限为 10MB。storage 以用户维度隔离……不同小程序之间也无法互相读写数据」 | 每个微信账号一份，天然按用户隔离 |
| 清理策略 | 「本地缓存的清理时机跟代码包一样，**只有在代码包被清理的时候本地缓存才会被清理**」 | **代码包正常版本更新不清理缓存**，所以「更新后存档还在」成立；用户删小游戏 / 清缓存才会丢 |
| `wx.getStorageInfoSync()` | 返回 `{ keys, currentSize, limitSize }`，大小单位 **KB** | 启动自检容量；`limitSize` 预期 10240 |
| `wx.onHide` / `wx.onShow` | 切后台 / 回前台 | `onHide` 同步落盘；`onShow` 检查快照 |
| `wx.getFileSystemManager()` 用户目录 | 有独立文件空间 | **不用**：JSON 快照 < 8 KB，storage 更简单 |
| **存档服务 · 得分存储**（`wx.getRankManager()`） | 平台级「统一的用户得分上报与查询服务」；官方场景 1 明确写了**进度存档**：「用户回流或换设备时，从平台查询其最高通关关卡」；`rankManager.update({ scoreKey, score })` 上报，`getScore({ periodType: 4 })` 查历史最高；`scoreKey` 需在 MP 后台「游戏玩法ID设置」配置 | **P1 跨设备进度信标**：把「最高到达层数 / 通关次数 / 解锁位掩码」编码成数字上报，换设备可恢复**进度感**。只存数字，存不了完整道具图鉴与局内快照 |
| 云开发 `wx.cloud`（数据库 / 云存储） | 按 `openid` 存取任意数据 | **P2 可选**：完整 meta 云备份；需开通云开发、有运维成本 |
| `wx.setUserCloudStorage`（开放数据域） | 仅好友排行榜用的键值 | **不可用于存档** |

官方还明确提醒：「storage 应只用来进行数据的持久化存储，不应用于运行时的数据传递或全局状态管理。**启动过程中过多的同步读写存储，会显著影响启动耗时**」——因此本作启动时只读 2 个键（meta + run 是否存在），其余延迟到进入游戏后。

**仍然需要真机确认的 3 件事**（文档只给出机制，不给具体数值与客户端行为）：

1. `wx.getStorageInfoSync().limitSize` 实测是否为 10240 KB；
2. 体验版 v1 打一局 → 发 v2 覆盖更新 → 「继续上局」是否仍在（按清理策略应当保留）；
3. 用户删除小游戏 / 清理缓存后，`run` 与 `meta` 同时消失时的降级表现（应当安静地从头开始，不报错）。

> 来源：
> - [wx.setStorageSync](https://developers.weixin.qq.com/minigame/dev/api/storage/wx.setStorageSync.html)（1 MB / 10 MB、持久化说明）
> - [本地缓存（存储策略）](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/storage.html)（隔离策略、清理策略）
> - [wx.getStorageInfoSync](https://developers.weixin.qq.com/minigame/dev/api/storage/wx.getStorageInfoSync.html)（返回字段与单位）
> - [得分存储（存档服务）](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/storage-server/storage-score.html)（进度存档场景、RankManager API）
> - [更新机制](https://developers.weixin.qq.com/minigame/dev/guide/runtime/update-mechanism.html)（版本更新流程）

### 13.6 Web / 桌面与微信的差异

| 环境 | 底层 | 备注 |
|---|---|---|
| 微信小游戏 | `wx.*StorageSync` | 主目标平台；10 MB；随版本更新保留 |
| 浏览器预览 | `localStorage` | 5 MB；按域名隔离；清站点数据会丢——预览时属正常 |
| 桌面调试 | 同上 | 用不同 key 后缀区分预览档与正式档，避免调试污染 |

### 13.7 验收要求

- 杀进程 / 切后台 / 刷新页面后都能从最后房间继续；
- 死亡后确认 `run` 键已删除，重新进入主界面不再出现「继续上局」；
- 手动把 `run` 键改成非法 JSON → 启动不崩、备份保留、meta 正常；
- 用内置 v1 样本启动 → 自动升到 v2，冰箱贴 / 图鉴 / 解锁不丢；
- **单 key < 1 MB、总量 < 10 MB；启动阶段只同步读 2 个键**（官方明确警告启动期同步读写影响启动耗时）；
- 真机覆盖安装新版本 → 上局进度仍在。

### 14.3 性能目标

| 项 | 目标 |
|---|---|
| 帧率 | 中端安卓（骁龙 6 系）稳定 **60fps**；微信真机不低于 50fps |
| 单帧逻辑 | `update()` + 碰撞 **< 8ms**（峰值）；渲染重绘 < 6ms |
| 实体上限 | 子弹 300 / 敌人 40（同屏存活）/ 粒子 120 |
| 内存 | JS 堆 < 80 MB；单帧 GC 分配尽量为 0（对象池复用 Bullet / Enemy） |
| 启动 | 首屏到可操作 < 3s（不含引擎初始化），启动期同步读 storage ≤ 2 次 |
| 包体 | 主包 ≤ 4 MB（`check-wechat-build.js` 会卡这条） |

> **运行时监控（M1 已内置 `FridgePerf`）**：Canvas 顶部中间「帧率」按钮 / 键盘 `F` 开关；
> 显示 FPS、帧时间均值与峰值、逻辑与渲染耗时、敌人 / 子弹 / 拾取物数量、JS 堆占用。
> 数据同时挂在 `globalThis.__fridgePerf` 供页内探针读取。
> 实测（桌面预览，40 敌同屏）：60fps、逻辑 0.04ms、渲染 0.56ms。

### 14.4 渲染

- 单 `Graphics` 每帧 `clear()` 重绘：地板、墙、门、实体、子弹、特效。
- 玩家用 3–4 层圆形（身体 / 高光 / 眼睛 / 道具挂件）；敌人用形状 + 颜色区分，不依赖贴图。
- 道具外观 = 玩家身上的小挂件（最多 4 个），其余用 HUD 图标表达；**不做每道具独立角色皮肤**（成本无底）。

## 15. 确定性与自检

世界内部只用一个 `mulberry32(seed)`：

- 地图生成、敌人刷位、掉落、商店货位全部走同一个 RNG，**调用顺序固定**。
- 弹幕角度由 `shotIndex` 递增；Boss 阶段由 HP 阈值切换。
- 同一 `seed + charId + 输入脚本`，两次运行逐位相同。

## 19. 风险与取舍

| 风险 | 影响 | 对策 |
|------|------|------|
| **手感不对** | 后面全白搭 | M1 单独验收；眼泪速度 / 命中断帧 / 击退先调爽 |
| 竖屏双指操作 | 右手挡住画面、误触 | 右半屏只在**拖动距离 > 8px** 才算瞄准；按钮节点拦截事件 |
| 内容量 | 40 道具 + 4 层 + 4 Boss 是 survivor 的 3 倍 | 全部程序化形状；道具外观只做 4 个挂件位 |
| 与 survivor 分流 | 两款肉鸽动作抢用户 | 定位差异写进大厅卡片描述；不共用存档 |

| 时长 | 12–15 分钟对超休闲仍偏长 | 「电梯」解锁从第 2 层开始；每日挑战单局更短；任意时刻可退 |
| **本地存档被清** | 用户删小游戏 / 清缓存 / 换设备 → 进度全丢 | 跨局 meta 小、可重建；备份键 + 坏档兜底；官方机制保证版本更新不清缓存；P1 用「得分存储」做跨设备进度信标 |
| **存档拖慢退出** | `onHide` 写盘阻塞 | 快照 < 8 KB、同步写入 < 5 ms；只写两个小键，不写战斗实体 |
