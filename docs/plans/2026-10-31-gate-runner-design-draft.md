---

## 1. 品类确认

用户描述：「往前走，发射子弹，左右两边都有选择，是 ×2 或者 ÷2 或者 +20」。

这是 **gate runner / count runner（数值门跑酷）**，代表作品：

- **Count Masters**（《人数大作战》）——小人队伍过 ×2/÷2 门，撞敌人减员
- **Number Gates** / **Crowd Runner** —— 同类换皮
- 抖音/微信小游戏里的「数字冲刺」「人数冲刺」多属此类

核心乐趣不是操作精度，而是**数值滚雪球的决策快感**：每次二选一都在「现在更强」和「之后更稳」之间下注，屏幕上的人数/伤害数字不断变大。

---

## 2. 核心循环

```
自动前进 → 遇到左右两道数值门 → 横移选一边 → 数值变化
        → 遇到敌人（挡路，需火力打掉）→ 边走边打，敌人同时消耗我方数值
        → 重复 → 终点 Boss → 结算（到达距离/最终数值/得分）
```

**单资源设计**：队伍数值 `count` 同时是**火力**和**血量**，不引入第二套资源。

- 火力：`dps = min(count, FIRE_CAP)`，每颗子弹 1 点伤害，子弹只是表现
- 血量：敌人存活期间按 `enemy.atk` 持续扣 `count`
- `count ≤ 0` → 立刻结束（比「走到终点」更常见的失败方式）

这样 ×2 门同时让你「打得更快」和「更耐打」，收益直观；÷2 门则双重惩罚，选择有分量。

## 3. 玩法规格

### 3.1 坐标与镜头

沿用项目约定：逻辑坐标原点左上、y 向下。玩家固定在屏幕下方，世界向下滚动。

| 常量 | 值 | 说明 |
|------|----|------|
| `PLAY_W` | 660 | |
| `PLAY_H` | 860 | |
| `PLAYER_Y` | 700 | 玩家所在屏幕 y |
| `PLAYER_X_MIN/MAX` | 90 / 570 | 横移范围 |
| `SCROLL_BASE` | 420 px/s | 起始前进速度 |
| `SCROLL_MAX` | 620 px/s | 随距离增长封顶 |
| `START_COUNT` | 20 | 初始人数 |
| `COUNT_MAX` | 9999 | 防溢出 |
| `FIRE_CAP` | 30 | 每秒最多 30 发（也是 DPS 上限） |
| `FIRE_INTERVAL` | 1/30 s | |
| `HIT_STOP_SEC` | 0.0 | 不做顿帧，保持跑酷节奏 |

### 3.2 数值门

- 成对出现，左门覆盖 `x ∈ [40, 320]`，右门覆盖 `x ∈ [340, 620]`，玩家中心落在哪边就触发哪边。
- 门的数值模板（每对随机抽一个，左右随机交换）：

| 模板 | 左 / 右 | 设计意图 |
|------|--------|----------|
| `×2 / ÷2` | 高风险高回报 | 经典 |
| `×3 / ÷2` | 更激进 | 后期出现 |
| `+20 / +50` | 纯加法 | 前期保底 |
| `×2 / +30` | 乘法 vs 加法 | 教学关用 |
| `−10 / ×2` | 付费换倍率 | 中后期 |
| `÷2 / +100` | 大数时的赌博 | 后期 |

- 触发后门变绿/变红并飘字，0.4 s 内不可重复触发。
- `count` 钳制在 `[0, 9999]`，÷2 向下取整但至少扣 1（避免 1 → 0 的隐形死亡）。

### 3.3 敌人

- 挡在路中间，宽度覆盖 2–4 条「身位」，必须绕不过去（或绕过去要贴边，v1 不允许绕）。
- 属性：`hp`、`atk`（每秒对 count 的伤害）、`width`。
- 玩家进入接触距离后停止前进，双方对拼：我方按 `dps` 扣血，敌方按 `atk` 扣 `count`。
- 敌人死亡 → 继续前进；`count ≤ 0` → 立即 game over。
- 敌人 HP/ATK 随距离增长：`hp = round(30 + 0.08 * distance)`，`atk = 2 + distance / 800`。
- **设计约束**：期望「同归于尽」——如果玩家一路选对门，打完敌人应剩 40%–70% 人数；一路选错则在第二个敌人处阵亡。

### 3.4 终点 Boss

- 距离 2400 px 处一个 Boss，HP 约为「当前期望 count × 2.2」，atk 为普通敌人的 1.5 倍。
- 击杀 Boss → 胜利结算；被耗死 → 失败结算。

### 3.5 关卡生成

- 世界由「段落」拼接，每段 `SEGMENT_LEN = 420 px`，按 seed 生成：
  - 第 1 段：教学，`×2 / +30` 门 + 无敌人
  - 第 2 段起：门 +（可选）敌人交替
  - 每 4 段必有一个敌人；每 6 段至少一个 `×` 门
- 全部走 `mulberry32(seed)`，与砖块远征一致；每日挑战直接固定 seed。

## 4. 表现（零美术）

| 元素 | 画法 |
|------|------|
| 队伍 | 最多 40 个小圆点按「方阵」排列（实际 count 可上千，超出用数字标签表示），圆点位置带轻微正弦抖动 |
| count 标签 | 队伍上方 `Label`，大号数字 |
| 数值门 | 左右各一块半透明色块（乘 = 蓝、除 = 红、加 = 绿、减 = 橙），中间 `Label` 写 `×2` / `÷2` / `+20` |
| 敌人 | 红色方块 + 头顶 HP 条（细实心矩形）+ 数字 |
| 子弹 | 从队伍前方周期性射出的 4×10 实心小矩形，命中后消失并溅 2 个碎屑 |
| 背景 | 深蓝底 + 向下滚动的横向细线（`rect + fill`，不用 `stroke`） |

色板沿用 `#151E33` 底、`#6EE7FF` 我方、`#FF6B6B` 敌方。

**性能**：子弹与碎屑都进对象池，硬上限 80 / 120；圆点用 `Graphics` 单次批量绘制，不用 40 个节点。

## 5. 输入

- **横移**：按住左右拖动，玩家 x 跟随手指（钳制在 `[90, 570]`）；松手不投放任何东西，继续前进。
- **点击左/右半屏**：可作为备选操作（一步横移 180 px），v1 不做，避免与拖拽冲突。
- 桌面端 `TOUCH_CANCEL` 只结束拖动，不触发任何数值逻辑。
- 触摸区与砖块远征一致：全屏 `InputArea`，面板为兄弟节点。

## 6. 状态机与事件

```
ready → running → (game_over | victory) → 结算面板 → 重开 / 返回大厅
```

纯逻辑事件（供表现层消费）：

```ts
type GateEvent =
  | { type: 'gate_hit'; side: 'left' | 'right'; op: 'mul' | 'div' | 'add' | 'sub'; value: number; before: number; after: number }
  | { type: 'enemy_engaged'; id: number; hp: number }
  | { type: 'enemy_destroyed'; id: number; x: number; y: number }
  | { type: 'squad_hit'; amount: number; count: number }
  | { type: 'boss_spawn'; hp: number }
  | { type: 'victory'; score: number; count: number; distance: number }
  | { type: 'game_over'; distance: number; count: number };
```

## 7. 代码结构

与砖块远征同构，继续保持「纯逻辑可无编辑器回归」：

```
assets/games/game_gate_runner/scripts/
├── GateConfig.ts     // 常量、门模板、敌人曲线、色板
├── GateCore.ts       // 纯逻辑：滚动、门触发、对拼、生成、结算
└── GateGame.ts       // Cocos 组件：Graphics + 触摸 + HUD/结算
tools/verify-gate-core.js
```

`GateCore` 对外只暴露 `startRun(seed)`、`step(dt)`、`setPlayerX(x)`、`popEvents()` 与只读状态（`count`、`distance`、`state`、`gates`、`enemies`）。

## 8. 回归测试（`tools/verify-gate-core.js`）

| # | 用例 | 判据 |
|---|------|------|
| 1 | 门模板 | 每对门左右各一个，操作类型合法，值 > 0 |
| 2 | 乘法/除法 | `×2` 后 count 翻倍；`÷2` 向下取整且至少扣 1 |
| 3 | 钳制 | 连续 ×3 不超 `COUNT_MAX`，不出现 NaN |
| 4 | 门只触发一次 | 同一门停留 2 s 只生效一次 |
| 5 | 敌人对拼 | dps 按 `min(count, FIRE_CAP)` 计算；敌方按 atk 扣血 |
| 6 | 敌人死亡后继续前进 | 距离恢复增长，事件顺序正确 |
| 7 | count 归零 | 立即 game_over，不再前进 |
| 8 | Boss | 到达距离后生成，击杀后 victory |
| 9 | 生成确定性 | 同 seed 同距离的门/敌人序列完全一致 |
| 10 | 生成合法性 | 不会出现「两道门都不可通过」或重叠段落 |
| 11 | 180 s 自动游玩 | 不崩溃、状态合法、能走到 Boss 或死亡 |
| 12 | 平衡性 | 一路选「更优门」能过 Boss，一路选「更差门」必死 |

## 10. 风险

| 风险 | 缓解 |
|------|------|
| 乘除法数值失控（几千人） | `COUNT_MAX` 封顶；显示层只画 40 个点 + 数字；DPS 封顶 30 |
| 门的选择「一眼就知道选哪边」 | 用「乘法 vs 大加法」制造临界点；后期引入「好门后面接强敌」的隐性代价（v2） |
| 方阵像一团糊 | 圆点半径随人数缩小，队形按 `ceil(sqrt(n))` 排布，上限 40 点 |
| 对拼节奏拖沓 | 敌人 HP 按「期望 dps × 1.2–2 s」反推，不做长时间拉锯 |
| 与砖块远征争夺触摸手势 | 两者都只用「拖动 + 点击」，逻辑独立，无共享组件 |
