## 一、判定尺与范围

| 维度 | 尺子 |
|------|------|
| 交互 | 设计 §2.2/§2.3/§4.1 的操作语义；改版方案 §4 的七项界面方案；实机能否走通、有无"静默失效" |

**走查路径**：职业选择 → 路线图 → 战斗①(布阵/移动/攻击/技能) → 胜利结算 → 升级三选一(选卡 + 跳过) → 战斗② → 商店(买技能/回血/离开) → 事件(流浪商人) → 战斗③ → 休息 → **Boss 战(连续 3 回合观察)** → 通关面板 → **返回大厅(切到 Lobby)** → 从大厅再进游戏 → 4 职业开局 → 战斗 → **失败 → 游戏结束面板 → 重新开始**。

### 加速与注入声明（哪些结论不是自然流程）

以下**只用了注入加速/布景**，界面与规则仍走真实代码路径与真实点击：

1. 战斗的**清场**（把敌人血量置 0 后调 `checkBattleEnd`）——为在合理轮次内覆盖全部面板；
2. **4 职业开局**的布阵与失败结局：布阵用 `battleManager.placeUnit()` 直接落位（布阵拖拽已在 3 职业局用**真实拖拽**验证过），"确认部署"仍**真实点击**；

## 二、问题清单（按严重度）

### A. 规则/交互正确性（会直接影响玩法判断）

#### A1（高）火球 AOE：预览 9 格、实伤只有 5 格 —— 预览在说谎

- **现象**：法师火球（`aoe_1radius`）的落点预览高亮完整 **3×3 = 9 格**，实际只对**曼哈顿距离 ≤ 1 的 5 格**（十字）造成伤害；对角落 4 格高亮了却打不到。
- **证据**：`BattleManager._getAoePreviewPositions()` 用 Chebyshev（`dr<=1 && dc<=1`）→ 9 格；`executeSkillEffects` 的 `case 'aoe_1radius'` 用曼哈顿（`|dr|+|dc| <= 1`）→ 5 格。同文件 L938-939 的注释明确写"aoe_3x3 与 aoe_1radius 都是 3×3"，与实现不符。
- **实测（真实操作）**：中心 (3,3)；剑兵 @(2,3)（正交）→ 6→**0 阵亡**；弩手 @(2,4)（**对角，在预览高亮内**）→ 4/4 **零伤害**。预览高亮色实测：9 格 `239,68,68,120` + 中心 `220`。
- **影响**：法师的起手技能必中，玩家据预览做取舍会直接打空；这是"看得见的承诺没有兑现"。
- **建议**：`aoe_1radius` 改用 `Math.abs(dr) <= 1 && Math.abs(dc) <= 1`（与预览、与"目标周围 1 格"文案一致）。`aoe_3x3` 与预览已一致，无需动。

#### A2（高）事件"花 10 金币买随机技能"会**收钱不给货**

- **现象**：0 号单位技能位已满时选该选项，金币照扣，技能一个没学到，界面无任何提示。
- **证据**：`applySingleEffect` 按 effects 顺序执行 —— `spend_gold` 无条件扣款并 `Math.max(0, ...)` 钳制；随后 `learn_skill` → `learnRandomSkillFor(playerUnits[0])`，因 `hasFreeSkillSlot === false` 返回 `null`，无补偿、无回滚。
- **实测**：金币 **95 → 85**，三个单位技能数 **3/1/2 → 3/1/2（完全不变）**。
- **对比**：商店的同名路径上一轮已修成"先学、成功才扣费"（`onShopBuySkill` 先 `learnRandomSkillFor` 再扣款），事件路径未同步。
- **附带（同一根因）**：商店与事件的"学技能"**只作用于 0 号单位**（`playerUnits[0]`），玩家无法选择给谁学；一旦 0 号满位，这两个效果对本局**永久失效**。
- **建议**：与商店同构 —— 先判定"能否学会"，成功才执行扣款；并把"学给哪个单位"变成可选（或至少给出"哪个单位学了什么"的反馈）。

#### A3（中）失败结算的荣誉数字虚报 21 倍

- **现象**：失败结算面板写"获得 **+21** 荣誉"，实际只入账 **+1**。
- **证据**：`onRunComplete(false)` → `const honorGain = this._runData.honor > 100 ? this._runData.honor - 100 : 0;` —— 公式假定"本局起点恒为 100"，而 `+100` 只在**通关**时加。实测 meta 荣誉 `120 → 121`（`onBattleEnd(false)` 给 `max(1, 0*5) = +1`），面板显示 `121 - 100 = 21`。
- **建议**：在开局时快照 `honorAtRunStart`，结算显示 `honor - honorAtRunStart`。

#### A4（中）队伍人数无上限：可 4 职业开局，按钮显示"(4/3)"

- **现象**：4 个职业全选后按钮文案变成"开始游戏 **(4/3)**"且**可点**，开局 4 个单位。
- **证据**：`updateStartBtnInteractable` 判定 `length >= 3`（无上限）；`onClassToggleClicked` 只在"减到最后一个"时禁止取消。实测点击 4 行 → `_selectedClasses = [warrior, archer, mage, cleric]`、`startDisabled: false`。
- **与设计冲突**：设计 §1/§2.2 明确"3 人小队 / 我方可操作 3 个单位"。且 4 人**明显更简单**：多一具肉盾、每场多一张升级卡、总输出更高，而**敌人数量与强度完全不随人数变化**（`_currentDifficulty = _battleCount`，与队伍规模无关）。
- **布局侧无问题**（已量化）：4 个槽位列 100×292 @x[10,110]、y[408,700]，与棋盘（x ≥ 120）、阶段条（y 1140-1180）、行动栏（y 134-206）**均无重叠**，槽间距 12 正常。
- **建议**：把上限收到 3（`length === 3` 时禁用未选行或替换最早选择），并把文案改成 `(${n}/3)` 的合法读数。

### B. 元素与视觉

#### B1（中）三个运行时按钮没有视觉底：等待/攻击按钮 `spriteFrame = null`，技能按钮连 Sprite 组件都没有

- **证据**（同一行动栏内对比）：
  - `BattleUI/ActionBar/EndTurnButton`：`Sprite frame=default_sprite_splash` ✓ 正常实心按钮；
  - `BattleUI/ActionBar/WaitButton` / `AttackButton`：**`frame = NULL`**（color 38,48,65 存在，但不绘制任何东西）；
  - `BattleUI/SkillButtonContainer/SkillBtnPrefab`：**无 `cc.Sprite` 组件**，只有一个 `skillLabel`（"火球 [3⚡]"）。
- **后果**：
  1. 同一行动栏里"结束回合"是实心蓝按钮，而"等待/攻击"是**裸文字**，可点感不一致；
  2. 技能按钮是浮在棋盘下方的裸文字；`Button.transition = COLOR` 的两个状态色**没有可着色的 Sprite** → 按下/悬停/禁用反馈全部不可见；
  3. 技能按钮在"无有效目标"时是 `interactable = false`，但**外观与可用时完全一致** → 玩家点了没反应且看不出原因（实测战士开局 `猛击 [2⚡]` 即为禁用态，视觉无差别）。
- **归属**：与 AGENTS 教训 C 同源（"只设 color 不设 spriteFrame ⇒ 什么都不画"）。
- **建议**：运行时统一补 `spriteFrame`（借项目已有的 `default_sprite_splash`，同 `getSolidSpriteFrame()` 的做法）；技能按钮补 Sprite 组件并接 `applyButtonTheme`，禁用态用 `PRIMARY_DISABLED`。

#### B2（中）"战斗开始！"的遮罩不绘制

- **证据**：`playBattleStartAnimation` 只 `tween(overlaySprite).to(0.3, { color: hex(BG_OVERLAY, ALPHA.BG_OVERLAY) })`；而 `BattleStartOverlay` 的 Sprite **`spriteFrame = null`**，750×1330 的"遮罩"**什么都不画**（tween 后实测 `color = 0,0,0,180`、`frame = NULL`）。
- **实测截图**：点"确认部署" 400ms 后，"战斗开始！"只是一小团橙字（scale≈0.3）直接**叠在棋盘与单位上**，全程无压暗背景。
- **建议**：给 `BattleStartOverlay` 补 `spriteFrame`（并顺手把 750×1330 收到画布内）。

#### B3（中）确认部署后，单位信息面板先露出场景占位文本"你好 / HP: 0/0"

- **证据**：场景里 `UnitInfoPanel/UnitNameLabel` 写死 `"你好"`、`HpLabel` 写死 `"HP: 0/0"`、`EnergyLabel` `"⚡ 0/5"`；`hideDeployPhase()` 会立刻 `setStatPanelVisible(true)`，而首个单位的信息要等 ~1.6s 进战斗动画结束、`selectNextPlayerUnit()` 才写入 → 实测截图里面板显示 **"你好 / HP 0/0 / ⚡ 0/5"**。
- **建议**：`hideDeployPhase()` 里先 `clearUnitInfo()`；场景占位文本换成空串（`"你好"` 是明显的调试残留）。

#### B4（低）商店 / 休息面板未纳入设计令牌，且按钮不会置灰

| 项 | 实测 | 令牌要求 |

| ShopPanel / RestPanel 尺寸 | 300×465 / 260×425 | 面板 ≤640×960、推荐 640 宽 |
| 按钮高度 | 买技能 **36** / 回血 **36** / 离开 **30** / 休息 **36** / 跳过 **36** | 统一 **48** |
| 按钮文字 | fs **16**（FONT_CAPTION） | FONT_BODY 20 |
| 买不起时的表现 | 金币 4 < 10，"买技能 - 10金币"**外观照旧可点**，点了**毫无反应**（仅 `console.info`） | 不可用项应可见地禁用 |

- 事件面板**已经做对**（金币不足 → "（金币不足）" + `TEXT_DISABLED` + `interactable=false`，实测 ✓），商店/休息未对齐 → 同一游戏内两套"不可用"表达。

### C. 完整度与设计落差

#### C1（高）敌人技能层整体未实现（设计 §5.1 / §5.2 / §5.3 全部落空）

- **证据**：`EnemyConfig.abilityIds` 全项目**检索不到任何读取点**；`ENEMIES`/`ELITE_ENEMIES` 的 `abilityIds` 全为 `[]`；`BOSS_CONFIG.abilityIds = ['boss_sweep','boss_summon']` 在 `SKILLS` 里**没有对应条目**，也没有任何处理分支。
- **实测**：Boss 战连续 3 回合（真实"结束回合"）
  - 敌人数**恒为 3** → 设计 §5.3 的「集结（每 2 回合召唤 1 个剑兵）」不存在；
  - 每回合只有 **1 名**玩家单位掉血（法师 5→2→0、弓手 6→0）→ 没有「横扫（前方 3 格直线 AOE）」；
  - 每个敌人的 `skills.length = 0` → 剑兵破甲斩 / 弩手速射 / 盾兵盾墙 / 影刺暗影步、精英四技能**全无**。
- **影响**：敌人退化成"属性块 + 走位"，设计里"敌人也有战术手段"的层次完全缺失；Boss 战尤其空（战争领主只是一只 20 血、7 攻的普通近战）。
- **建议**：把敌人技能接进现有 `executeSkillEffects` + `AIController`（`abilityIds` 已有字段与冷却语义可直接用），至少先补 Boss 两个技能。

#### C2（中）难度曲线只涨血量，攻击/防御永不成长

- **证据**：`createEnemyUnits` 里 `stats: { ...ENEMIES[i].stats, hp: Math.floor(...* (1 + difficulty * 0.1)) }` —— **只有 hp 被缩放**。
- **实测**：战斗① 剑兵 atk3；战斗④ 剑兵 atk3、盾兵 atk2、影刺 atk4（阴影/后期阶段攻击力与基础值完全相同，仅 hp 6→7、10→12）。
- **与设计冲突**：§5.5 明示"基础属性 ×1.2~1.4 / ×1.5~1.8"。玩家靠升级/商店涨血涨攻后，中后期伤害压力趋近于 0。
- **建议**：把倍率同时作用于 attack/defense（可给一个小折扣），并把倍率做成设计表里的常量。

#### C3（中）局外成长是"死数据"：荣誉只进不出，解锁永远不可见

- **证据**：
  - `honor` 会累积（每关 +5、通关 +100、失败 `max(1, battleCount*5)`）并写入 meta ✓，但 **`TALENTS`（9 项天赋）没有任何 UI 或消费点**；
  - 9 种天赋效果类型（`bonus_attack` / `bonus_class_attack` / `bonus_defense` / `bonus_hp` / `bonus_energy_max` / `bonus_energy_regen` / `bonus_gold` / `shop_discount` / `event_luck`）在代码里**没有任何 case 分支**；
  - `checkAchievements()` 往 `unlockedClasses` 里塞 `knight` / `assassin`（实测通关后 meta 确实多了 `knight`），而职业选择界面用硬编码 `CLASS_ORDER = ['warrior','archer','mage','cleric']`、`CLASSES` 也只有 4 项 → **解锁既不可见也无效果**。
- **影响**：设计 §6.2"成就 + 荣誉天赋树"双轨成长目前只落了"荣誉数字"，玩家没有任何可消费的成长出口。
- **建议**：要么补天赋面板（消费 honor 并应用上述 9 种效果），要么在文档里把 §6.2 明确标为 P1/P2 未实现，避免"看着有、其实没有"。

#### C4（中）路线图分支可全部走完，"选路"不复存在

- **证据**：`RouteMapUI.isReachable(id)` = "存在某个**已完成**节点连向我"。
- **实测**：完成节点 0 后 `1=true, 2=true`；完成节点 **2** 后 `1` **依然 true**（0 仍是已完成且连向 2 的兄弟 1），同时 `3=true` → **一局可把 10 个节点全部清完**（进度文案"已通关 N/10"也印证这个设定）。
- **与设计冲突**：§4.1 是树形路线（在岔路**选一条**），缺少互斥约束会让玩家"我全都要"，把金币/升级刷满再打 Boss，肉鸽取舍被削弱。
- **建议**：完成某节点后，把同一层的**兄弟节点**标记为不可达（或 `isReachable` 增加"该节点的所有前驱中已有其它兄弟被完成 → 不可达"）。

#### C5（低）数据驱动原则的破口：两个 effect 类型声明了但无人消费

- `passive_counter`（反击）、`passive_poison`（淬毒箭）在 `GameData` 里声明为 effect 类型，但代码里**从不读取**——两者实际是硬编码按技能 id 生效的：`takeDamage()` 里 `hasPassive('counter')`、`executeAttack()/executeSkillEffects()` 里 `hasPassive('poison_arrows')`。
- **功能是好的**（反击/中毒都会触发），只是与 `passive_toughness / passive_eagle_eye / passive_energy_regen / passive_aura_heal`（这四个走 effect）不一致 → 改数值时容易改了一处漏一处。
- **建议**：统一成 effect 驱动，或在数据里注明"该 effect 类型由 id 特殊处理"。

#### C6（低）其他落差

| # | 项 | 实测 / 设计 |
|---|----|-----------|
| 1 | 商店买技能**只作用于 0 号单位**（同 A2 附带） | 玩家无法选择受益者 |
| 2 | 路线图 10 节点 | 设计 §4.1 的树是 12 节点（6 战斗 / 2 精英 / 商店 / 休息 / 事件 / Boss，实测 4 战斗 / 2 精英 / 各 1） |

## 四、探针自纠（避免污染修复清单）

按 [`../tech/browser-verify-cocos-preview.md`](../tech/browser-verify-cocos-preview.md) §7 的纪律，记录本轮**看似缺陷、实为探针问题**的两处：

1. **"升级进度条首格就满格（592/592）"——不成立。** `progressBarFill.setScale(ratio)` 是**缩放**实现，我第一次用 `UITransform.width` 读（得到未缩放的 592），第二次用 `getBoundingBoxToWorld()` 读（得到 197.3 = 592×(1/3) ✓ 正确）。同一个对象两个探针读法给出不同答案，是探针问题。
2. **"单位名与 (1/3) 重叠"——不成立。** 名字标签 x[140,228]、`(1/3)` x[250.7,320]，相差 22.7px 无交叠；截图上"看着叠"是低分辨率错觉。真正的问题是**同一面板里名字出现两次**（信息重复），而非重叠。
3. 另：第一版重叠探针**只比较带 Sprite 的兄弟节点**，会漏掉"纯 Label 之间的重叠"（也正因如此上面第 2 条才会被误报）。用它做量化审计时需补一遍 Label 参与的比较。
