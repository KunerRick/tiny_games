# 合成大西瓜（merge）物理方案可行性评估

> 日期：2026-10-31
> 状态：评估完成，建议自研圆形物理
> 关联：[`2026-10-31-next-games-roadmap.md`](./2026-10-31-next-games-roadmap.md)、[`2026-10-31-game-brick-breaker-design.md`](../specs/2026-10-31-game-brick-breaker-design.md)

---

## 1. 结论

**建议自研「纯圆形」2D 物理（约 400–500 行），不启用 Box2D。**

理由按权重排序：

1. **形状同质**：场上所有物体都是圆，碰撞只需要「圆-圆」和「圆-墙」两类，Box2D 的多边形 SAT、关节、CCD 全部用不上。
2. **确定性可测**：自研求解器在固定步长下逐位可复现，能直接复用 `tools/verify-*-core.js` 的无编辑器回归范式；Box2D 跨平台一致性没有保证，做不了有意义的每日挑战复现。
3. **手感可控**：合成类游戏的核心手感是「堆叠稳、合并脆、下落不粘」，需要对恢复系数、摩擦、位置修正做细粒度调参；Box2D 的可调面反而更窄。
4. **包体与首包风险**：项目主包上限 4 MB（`tools/check-wechat-build.js` 会拦），引入 2D 物理模块会额外占用主包体积与初始化时间，而它 90% 的功能用不到。
5. **失败可回退**：若自研方案在 2 天内达不到「10 层堆叠不抖」的验收线，再切 Box2D；物理层被 `MergeCore` 的接口隔离，替换成本可控。

唯一让 Box2D 更省事的是「水果不是正圆」的视觉表现——但圆形水果的旋转本来就是假的（只需要按速度给贴图/色块加一点旋转），不影响碰撞。

---

## 2. 玩法对物理的最低要求

| 需求 | 说明 | 对求解器的含义 |
|------|------|----------------|
| 稳定堆叠 | 10+ 个水果叠成塔不抖、不缓慢下陷 | 位置修正 + 多次迭代 + 低速休眠 |
| 不穿透 | 高速下落不穿底、不穿墙、不穿其它水果 | 固定子步 + 速度上限 |
| 合并 | 同层接触 → 合成下一层，位置取中点 | 碰撞检测后每帧收集、去重、顺序处理 |
| 防爆堆 | 大水果生成时与邻居重叠要能推开 | 位置修正强度 + 迭代次数 |
| 游戏结束 | 水果停在警戒线上方 | 需要「静止」判定，不能瞬时误判 |

## 3. 方案对比

| 维度 | 自研圆形物理 | 内置 Box2D（`PhysicsSystem2D`） |
|------|-------------|-------------------------------|
| 依赖 | 0（纯 TS，可在 Node 跑） | 引擎物理模块，构建时进主包 |
| 包体影响 | ≈ 0 | 需实测，预估数百 KB 量级 |
| 确定性 | 固定步长下完全可复现 | 跨平台不保证，同平台同版本可近似 |
| 调参粒度 | 直接改常量，逐项可测 | 透过引擎参数，部分行为不可控 |
| 堆叠稳定性 | 需要自己调（本方案的主要工作量） | 开箱较好，但重水果压轻水果仍会抖 |
| 开发量 | 中（核心 400–500 行 + 单测） | 低（搭节点 + 配碰撞组），但调手感时间不可控 |
| 微信风险 | 低（纯 JS/TS） | 中（模块体积、初始化、不同版本行为） |
| 替换成本 | 物理层通过接口隔离，可整体替换 | — |

**判定**：先做自研。若堆叠稳定性在 2 天内无法收敛，再切 Box2D——`MergeCore` 对外只暴露「水果列表 + 每帧推进」，替换时只改内部。

## 4. 自研方案设计

### 4.1 坐标与常量

沿用砖块远征的约定：**逻辑坐标原点左上、x 向右、y 向下**，渲染层负责映射。

| 常量 | 建议值 | 备注 |
|------|--------|------|
| `PLAY_W` | 660 | 与砖块远征一致，便于共用布局 |
| `PLAY_H` | 860 | |
| `WALL_T` | 24 | 左右墙与底部的视觉厚度 |
| `DROP_Y` | 96 | 待落水果的悬挂高度 |
| `GRAVITY` | 2000 px/s² | |
| `FIXED_STEP` | 1/240 s | 与砖块远征相同，下落速度 2400 时每步 10 px |
| `MAX_SPEED` | 2400 px/s | 超过则截断，防穿透 |
| `ITERATIONS` | 8 | 位置修正迭代 |
| `RESTITUTION` | 0.05 | 水果几乎不弹 |
| `FRICTION` | 0.4 | 切向冲量系数 |
| `LINEAR_DAMPING` | 0.2 /s | 抑制长尾漂移 |
| `SLEEP_SPEED` | 12 px/s | 低于该速度累计 0.4 s 进入休眠 |
| `GAME_OVER_LINE` | 150 | 警戒线 y |
| `GAME_OVER_HOLD` | 2.0 s | 持续超过警戒线才判负 |

**生成尺寸**：11 层，半径 `22, 28, 34, 41, 49, 58, 68, 79, 91, 104, 118`（直径最大 236，宽 660 可并排 2 个大果）。只生成前 5 层（半径 ≤ 58），按权重 `[30, 26, 20, 14, 10]`。

### 4.2 求解顺序（每个子步）

```
1. 速度积分：v += g·dt；v *= (1 - damping·dt)；|v| 截断到 MAX_SPEED
2. 位置积分：p += v·dt
3. 圆-墙碰撞：位置钳制 + 法向速度反射（restitution）
4. 圆-圆碰撞（两两，n ≤ 120 时 O(n²) 完全够）：
   - 求重叠深度 depth = r1 + r2 - dist
   - 位置修正：按质量反比推开，各 depth/2 × CORRECTION(0.8)
   - 法向冲量：抵消相对法向速度 + 摩擦切向冲量
5. 重复 3–4 共 ITERATIONS 次（只做位置修正，速度冲量只在第 1 次做）
6. 休眠判定：速度低于阈值累计计时，超时后 v=0（被撞或合并时唤醒）
7. 合并检测：收集所有「同层且接触」的对，去重后按顺序处理
8. 游戏结束检测：静止且中心在警戒线上方累计超时
```

**关键细节**

- **位置修正与速度分离**：多次迭代只推位置，避免能量注入导致「越叠越弹」。
- **质量取面积**：`m = r²`，大果压小果时小果被推开更多，观感自然。
- **重叠容差**：`depth < 0.5 px` 视为接触但不修正，防止抖动。
- **合并的链式防抖**：同一帧内，合并产生的新水果**不参与本帧再次合并**；下一帧才允许。否则一次碰撞可能连续升 3 级。
- **生成重叠**：新水果落点若与现有水果重叠，先做一次 8 次迭代的位置推开，再进入正常模拟。

### 4.3 合并与计分

- 同层两圆接触（`dist ≤ r1 + r2 + 1.5`）→ 合并为 `tier+1`，位置取两圆中点，速度取质量加权平均并衰减 50%。
- 顶层（第 11 层）再合并：两个最大果碰撞直接消除并给高分（或作为「得分果」），不做第 12 层。
- 计分：`score += (tier+1) * (tier+2) / 2 * 10`（三角数，越高级收益越大），连击在 0.5 s 内连续合并时 ×1.5 / ×2 递增，封顶 ×3。
- 合并粒子：与砖块远征复用同一套「碎屑」表现，不新增系统。

### 4.4 操作

- 按住左右拖动：待落水果跟随手指（钳制在墙内 `r + WALL_T`）。
- 松手投放：`TOUCH_END` 投放；桌面端 `TOUCH_CANCEL` 不投放（与砖块远征一致）。
- 投放冷却 0.35 s；冷却期间顶部显示下一颗预览，但不允许连续点击刷果。
- 点击（位移 < 12 px）等价于在当前位置投放——避免「只想点一下」被拖拽阈值吃掉（踩坑手册 §11.6）。

### 4.5 失败判定

水果**静止**且中心 `y < GAME_OVER_LINE` 持续 2 s → 游戏结束。用「静止 + 持续」两个条件，避免水果在下落瞬间穿过警戒线就误判。

## 5. 无编辑器验证（`tools/verify-merge-core.js`）

参照 `verify-tetris-core.js` / `verify-brick-core.js`：`tsc` 编译 `MergeConfig.ts` + `MergeCore.ts` 到 `temp/merge-core-test/`，Node 断言。

| # | 用例 | 判据 |
|---|------|------|
| 1 | 单果自由落体 | 触底后速度 < 5，位置稳定 |
| 2 | 两果竖直叠放 5 s | 相对位移 < 0.5 px，无 NaN |
| 3 | 10 果堆塔 10 s | 总高度变化 < 2 px，无爆散（最大速度 < 100） |
| 4 | 同层接触合并 | 数量 −1、层级 +1、位置为中点 |
| 5 | 禁链式 | 三颗同层相邻，一帧只升一级 |
| 6 | 顶果消除 | 两个最大果合并后数量 −2，得分增加 |
| 7 | 墙内钳制 | 投放 x 在 `[r+WALL_T, W-…]`，永不越界 |
| 8 | 高速下落 | 从顶部以 2400 px/s 下落不穿底 |
| 9 | 确定性 | 同 seed 两次跑 30 s，水果位置逐位相同 |
| 10 | 失败判定 | 堆过警戒线且静止 2 s 后 game_over；短暂穿过不判负 |
| 11 | 投放冷却 | 冷却内 `drop()` 返回 false |
| 12 | 长跑 | 自动投放 500 颗不崩溃、状态合法 |

验收线：12 项全绿；堆塔 10 s 最大速度 < 100 px/s（不抖）。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 堆叠抖动/下陷 | 手感崩坏 | 位置修正 + 休眠；验收加「10 秒高度漂移 < 2 px」 |
| 大果生成爆堆 | 水果飞出屏幕 | 生成后做隔离位置修正 + 速度上限；单测覆盖 |
| 合并链式 | 分数暴涨、层级跳变 | 同帧新果不再合并；单测覆盖 |
| O(n²) 性能 | 低端机掉帧 | 上限 120 个水果（超过则最早的水果淡出），n=120 时 7140 对/子步 × 4 子步/帧，实测再决定是否加网格 |
| 触控阈值吃掉点击 | 点一下不投放 | 位移 < 12 px 视为点击投放 |
| 微信构建体积 | 主包超限 | 纯 TS，无新增依赖；构建后跑 `check-wechat-build.js` |

## 8. 待定项

1. 顶层水果碰撞是「消除得分」还是「继续堆着当障碍」——影响后期难度曲线，实现时先用消除，试玩后再定。
2. 是否加入「水果种类随关卡解锁」（前期只出 6 种，降低认知负担）——v1 先全开。
3. 每日挑战需要确定性，自研方案可直接用 seed；Box2D 方案则放弃该玩法。
