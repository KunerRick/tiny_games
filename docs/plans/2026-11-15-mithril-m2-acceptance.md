## 2. 规则落地（与设计对齐的数值）

- **词条点预算**：`itemAffixPoints = round(ilvl / 10)`，ilvl40 每件 4 点 → 8 槽共 32 点，与 §4.3 一致。
- **品质收敛**：权重随装等上移（common 52→13，epic 4→13，legendary 0.8→3.8，mythic 0.2→1.4）。
  `minQuality` 保底用于「重复刷本必出紫装」。
- **词条数** = `min(4, 品质条数, 点预算)`：ilvl10 的紫装仍然只有 1 词条 1 点 —— 品质只改颜色与词条**上限**，不会凭空加点（否则 1 级紫装就能顶满 32 点曲线）。
- **主手基型按职业分带**：战士 0/1、法师 2/3、游侠 4/5、牧师 6/7，其它槽位随机。
- **首通固定紫装**：`mine` → ilvl 8+4 = 12 的对应职业主手（战士 `mainHand_0` 秘银巨剑），带 50% 概率改造词条；重复刷本走 `minQuality:'epic'` 随机。
- **耐力**：`round(ilvl × 0.5)` 点/件，1 点 = 10 生命，不占词条位。
- **背包**：上限 60；满包拒绝入包、卸下失败（装备不丢）、换装不占新格（旧件回原位）；
  满包时的 BOSS 掉落自动折金币（`20 + ilvl×2`）并 toast 提示。
  **首通只在奖励真正入包时才消耗**：满包那一轮首通紫装保留，清出格子后再通关仍可领取。
- **uid 撞车**：固定种子重刷会生成同 uid 的货。入包时自动改名 `uid-1/2/…` 后保留，
  只有**背包满**才算失败（不再把撞车误报成「背包已满」）。
- **出售**：`round((3 + ilvl×0.6) × 品质档位)`。
- **出战 profile**：装备词条逐件求和后按 cap 收敛；`minIlvl` 只作**空档地板**（取 max，不相加）——
  ilvl40 均衡配点本身已触顶，相加会让毕业装词条全部浪费。
  主属性按设计 §4.1 单独给倍率：`gearApMultiplier(ilvl) = 1 + 0.6×(ilvl−1)/39`
  （空装 ilvl=1 ⇒ 1.00×，切片基线不变；ilvl12 首通紫武 ⇒ 1.17×）。

## 3. 纯逻辑自检

```bash
node tools/verify-mithril-core.js    # MITHRIL_CORE_OK 172/172（M1 + M2）
```

新增 148–172 共 25 项，分组：

| 组 | 覆盖 |
|---|---|
| 品质 | 权重随装等上移且全为正、2000 次只出合法品质、`minQuality` 500 次保底 |
| rollItem | 1000 件点数总和 = 装等预算、词条数 = min(品质, 预算, 4)、id 互不重复且合法、单条不超单点上限、ilvl10 紫装不凭空加点、同种子完全一致、主手按职业分带 300 次 |
| 副本掉落 | 首通固定紫装主手 ilvl = 副本 +4、重复刷 500 次全 ≥ 紫 |
| 属性聚合 | 空装备全 0 / 装等 1、两件装备逐件求和（暴击 5 点 = 18.75%、耐力 10 点 = +100 生命） |
| 背包 | 满包拒绝、重复 uid 与已装备件拒绝、换装回原位、卸下成功 / 满包失败不丢件、出售加金币、排序口径 |
| 存档 | serialize → parse 往返（背包 / 等级 / 金币 / 词条全保留）、坏档与无档回落默认、uid 冲突改名不丢件 |
| profile | 穿装抬升攻击强度（ilvl40 = 1.60×）/ 生命 / 副属性、`minIlvl` 地板只抬副属性、不改主属性 |

> **自检抓到的真 bug（第 172 项）**：`profileFromSave` 最初把 `critChance/haste/...` 直接写成装备求和，
> 等于把 `makeProfile(…, ilvl)` 算出的副属性整段覆盖 —— `minIlvl` 地板完全没生效。
> 修法：地板与装备取 **max**（不是相加），并新增注释说明为什么不能相加。

**平衡回归**：空档 + `minIlvl=5` 的 profile 与 M1 的 `makeProfile('warrior', 5, 5)` **逐字段完全相同**
（AP 11.379 / 生命 132 / 暴击 3.75% / 急速 2.5% / 精通 2.5% / 全能 1.25%），
所以 M1 的自动通关闸门（145/146）继续有效，M2 没有偷偷改战斗难度。

## 4. 浏览器实机验收（2026-11-14 夜 · `http://127.0.0.1:7456/`）

**点击坐标标定**（本轮新发现，补进手册）：canvas 元素 393×678.55，视口 720×1280 按 **fit-height** 缩放，
`k = min(w/720, h/1280) = 0.53011`，`offsetX = (w − 720k)/2 = 5.66`。
先前按 fit-width（k=0.54583）点「穿上」偏了 17 px（按钮半高 15 px）→ 表现为「点了没反应」，
`touch-start/end` 计数器为 0 才定位到偏差，而不是逻辑失效。

## 5. 独立复核（9 条发现，全部处理）

| # | 级别 | 发现 | 修法 / 验证 |
|---|------|------|-------------|
| 1 | **高** | `close()` 只关 `_panel`，全屏遮罩（含 `BlockInputEvents`）留在场上：返回后画面变暗、战斗触摸被吞到下次重载 | 显隐改由 `Menu` 整棵树 `_root` 负责；`isOpen()` 同步看 `_root`。实测：开面板拖拽 → 位移 0 / `core.time` 不动；关面板拖拽 → 位移 133.85 px / 时间前进 0.58 s |
| 2 | 中 | 固定 `seed` 重刷时掉落 uid 相同 → 入包被拒，被误报成「背包已满」并折金币 | `addToInventory` 撞车改名保留（与坏档 sanitize 同口径），只有满包才失败。实测同种子连刷两次：`it_mza5b` / `it_mza5b-1`，金币补偿 0 |
| 3 | 中 | 设计 §4.1 的装备主属性倍率（ilvl 1–40 = 1.60×）没接进实战 profile | 新增 `gearApMultiplier`，`profileFromSave` 用它乘 `attackPower`；空装 ilvl=1 ⇒ 1.00×，M1 基线不变。自检 171 改为严格 1.60×，172 断言地板不改主属性 |
| 4 | 中 | 选槽位时「出售」按钮可见但点了没反应；满包卸下静默失败 | 出售只对背包件显示；卸下失败把提示行改成红字「背包已满，先出售或换装一件再卸下」（下次交互自动复位） |

## 6. 已知取舍（M3 会消解）

1. **装备下一局生效**：面板第三行明写「装备变更将在下一局生效」，避免「换装当场 DPS 变了」的错觉。
2. **1 点急速 = 2.5% 恰好等于地板**，所以首件紫装只体现出生命与装等；掉装等升到 20+ 后词条才会盖过地板。
3. **入口只有**结算面板「装备」按钮 + 键盘 B（桌面）；手机常驻入口等 M3 营地一起做。
4. 改造词条（荆棘等）当前只做展示与存档，效果已在设计里排到 M4（与饰品一起接进战斗）。
